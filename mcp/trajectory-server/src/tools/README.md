# src/tools

The MCP tool modules for the trajectory server — one TypeScript file per domain. Each module exports a factory (e.g. `issueTools(db)`) returning `{ definitions, handlers }`: the JSON-Schema tool definitions Claude sees and the handlers that run against the SQLite trajectory DB (and, for some, the kuzu world-model graph). `index.ts` wires every module's definitions + handlers together and decorates each with the `agent` param used for role-gating.

A repo's git remotes live in `repo_remotes`; every tool reads and writes them through `../repos/remotes.ts` (`repoRemotes`, `syncRemotes`, `setRemoteSync`, `primaryRemote`, `upsertRepoRemotes`) — `scan_run` and `onboard_apply` write the git facts (name, url, provider, primary), and `pr_monitor_comments_get`, `repo_rename` and `onboard_state_get` read every row (PR/MR lookup follows the git push remote, not the sync choice). A row's `sync` flag is the Human's onboard Remote choice: `onboard_apply`'s `remote` answer (`setRemoteSync`) marks one remote per chosen provider and clears the rest; a new row starts at `sync = is_primary`, and `scan_run` never changes it. Issue and milestone sync read only the `sync = 1` rows (`syncRemotes`), so a provider without one is never spawned, even under `issue_sync = 'both'`. `onboard_state_get` / `onboard_apply` report remotes as `[{name, provider, url, sync}]`, primary first; `onboard_apply`'s `applied.remotes` lists only the representative repo's `sync = 1` rows.

`onboard-hooks-shim.ts` is a non-tool helper: when the project opts in (`headless_enforcement: yes`, set on request by `onboard_apply` with `headless_enforcement` alone on an onboarded project, after the `headless-intent` hint's consent; it is not an `/onboard` round), it writes the plugin's PreToolUse gates into the project's `.claude/settings.local.json` so they fire in non-interactive `claude -p` runs, where marketplace plugin hooks are absent; `no` removes them. It writes nothing outside the project. `onboard-sandbox.ts` writes or removes Claude Code's Bash sandbox block in the same file (`sandbox_enforcement`, default no): the filesystem `allowWrite` paths and the network `allowedDomains` TMB's remote commands need. When either writer creates `settings.local.json` in a git work tree that does not ignore it, `ensureLocalSettingsIgnored` (`onboard-sandbox.ts`) appends `.claude/settings.local.json` to the project's `.gitignore`; the sandbox result reports it as `gitignore_appended`. `onboard-scan.ts` is the `/onboard` pre-scan behind `onboard_state_get`'s `scan` key: offline git evidence per `repos` row (long-lived branches, `origin/HEAD`, first-parent merge counts, CI files, `CONTRIBUTING.md`), a branching recommendation with a confidence level, and a workspace summary, persisted in `repos.onboard_scan`; it never spawns gh/glab. `agent-runs.ts` opens and closes `agent_runs` rows with their `root_dir`, `host` and `exit_reason`; `containment.ts` holds the `outside_project` check the path-taking tools share. `lifecycle.ts` holds the issue/task lifecycle rules `issue_close`, `bro_atomic_close`, `task_recover` and `task_update_status` share: the live-task set, the passing-review rule behind `review_gate_bypassed` / `tasks_without_review`, the `issue_close` cascade, and the stale-running sweep.

Remote issue close: when `issue_close`, `bro_atomic_close` or `task_recover` closes an issue that is linked to GitHub/GitLab (`gh_iid` / `gl_iid`), it closes the remote twin only if `remoteSyncGate` (`sync/backend.ts`) is on — `TMB_DISABLE_REMOTE_SYNC` unset, `plugin_config.issue_sync` not `off`, and a usable gh/glab for the issue repo's remotes. The result carries `remote: {synced, skipped?, remotes: [{remote_kind, remote_iid, closed, skipped?}]}` (on `bro_atomic_close` / `task_recover` only when the issue closed): a linked remote whose provider has no `sync = 1` row is not spawned and carries `skipped: 'not_synced'`; `synced` is true when at least one synced remote was attempted and every one of them closed; the top-level `skipped` is `issue_sync_off`, `env_disabled` or `no_backend` when the gate was off, in which case nothing was spawned and one `issue_close_remote_skipped` audit row records the reason. An issue with no remote link returns `{synced: false, remotes: []}`. `issue_sync_retry` returns `{skipped: true, reason: 'not_synced'}` when none of the issue's backends has a sync row.

`milestone_close` closes the milestone on each synced remote and returns `remote_results: [{backend, slug, status, reason?, message?}]` (also in the `milestone_closed` audit content): `status` is `closed`, `skipped` (the remote has no such milestone, `not_found`) or `failed`. `remote_closed` is true when the gate was on, at least one target ran and none failed; `_sync` appears only on a failure, its hint naming the failed hosts.

## How it fits

`task_brief` returns the task's typed `verification[]` commands and `verification_run`: the latest run of them the close gate recorded (`{run_id, commit_sha, source, started_at, finished_at, exit_code, timed_out, budget_s, commands: [{ordinal, command, exit_code, elapsed_s}]}`, null when none), so bro and pr-reviewer read the result instead of running the commands again. `validation_history` rows carry the same shape as `verification_run` — the latest run started by the attempt's `created_at`. The shared reader is `verification-runs.ts`.

These modules are the entire MCP surface bro and the subagents call. `index.ts` is the registration point; role-gating per tool is enforced by `requireRoles()` in `../middleware/agent-scope.ts`. See `../../README.md` for the tool-family overview, environment, and schema notes. Handlers are unit-tested at L2 (`../test/`).

## Discussions: single insert+embed path

Every discussion write — `discussion_append` plus every composite that logs an `intent` / `decision` / `note` (`task_provision`, `intent_start`, `task_retry`, `bro_verification_fail_record`) — goes through one helper, `insertDiscussion(db, { issue_id, author, kind, body, created_at?, repo?, remote_comment_id? })` in `discussions.ts`. It INSERTs the row and fires `embedAndStore` so the entry is indexed for semantic `discussion_search`. The embed is not awaited and its failure is caught (degrades to FTS-only), so when a composite calls it inside `db.transaction()` the embedding write lands after COMMIT and an embed failure never rolls back the transaction. No module writes the `discussions` table directly. `pr_monitor_comments_get` persists each fetched PR/MR comment through it with `remote_comment_id = '<provider>:<pr_number>:<comment_id>'`; on that key the INSERT is `ON CONFLICT DO NOTHING` against the partial UNIQUE index, so an already-stored comment returns null and is neither inserted nor embedded. The tool result is the fetch payload (`comments`, `pr_state`, `remote_kind`, `head_branch`) plus `persisted` (new rows) and `duplicates` (comments already stored); the carrier is the issue of the PR's task (`pr_review_runs.task_id`, else the most recently updated task on the head branch), closed tasks included and failed or escalated ones skipped. When the PR's slug maps to a registered repo, only that repo's tasks (and legacy tasks with no repo) qualify; when it maps to none, the newest-updated matching task across all repos wins. Both counts are 0 when no task carries the PR.

## Audit: who may write which event

Every audit row goes through `insertAudit` (`audit.ts`). Each event in `../audit-events.ts` lists its `writers` — the agent roles that may author it, `server`, or `hook`. `audit_append` takes the role from the `agent` arg (the same `normalizeAgent` path `requireRoles` uses), refuses an event whose writers omit that role with `audit_event_not_writable_by_role` (`event_type`, `caller_role`, `allowed_writers`), and records `from_node` as the caller itself — `bro`, `swe`, `pr-reviewer`, or a consultant's name; a `from_node` arg naming anyone else is refused. `insertAudit` runs the same check when given `writer`. So no agent but bro can write a gate waiver (`verification_gate_waived` is hook-only), and `GATE_SKIP_RECORDED_SQL` (`lifecycle.ts`) counts a review waiver only when `from_node = 'bro'`.

## Atomicity notes

`task_provision` is atomic from the caller's view: it resolves the repo path and validates the branch `base` (`git rev-parse` on `origin/<base>`), then creates the branch ref, all **before** committing the decision + task transaction. A git-setup failure (unresolvable repo or base, failed branch creation) returns a tool error and persists nothing — no orphan task row is left occupying the `(issue_id, branch_id)` UNIQUE constraint, so the same `branch_id` retries cleanly once the repo/base resolves. Only worktree creation stays fail-soft (post-commit, recoverable): a worktree failure returns `git_setup:'error'` with a diagnostic but keeps the committed task. `git_setup:'created'` means a new ref from `base`; an existing local or origin ref at or behind the base tip is fast-forwarded and reported `'reused'`; a diverged ref is refused with `branch_exists_diverged` (ref, ahead/behind distance, open PRs read with `gh pr list --head` / `glab mr list --source-branch` under the issue-sync gate) unless `reuse_existing: true` keeps it as-is (`'reused'`). `worktree_reused` reports an existing worktree separately.

`agent_register`, `agent_list` and `agent_resolve` speak one `file_path` shape: `plugin:<path>` (relative to the installed plugin root, resolved via `resolvePluginRoot()`) or `project:<path>` (relative to the workspace root derived from the DB path); an unmarked path is refused with `invalid_file_path`. Every returned agent row carries the absolute `resolved_path` (null for a `project:` path when the DB is `:memory:`). `swe` and `pr-reviewer` must be `plugin:` — a `project:` registration under those names would shadow the backbone and is refused. `agent_register` with a `project:` path promotes a `plugin:` consultant row and audits `tmb_agent_created`; `agent_list` filters by `root` (`plugin` / `project`); `agent_resolve` (bro only) takes an optional target `file_path` (default `project:.claude/agents/<name>.md`) and returns it with its `resolved_path` and the creation mode.

`agent_runs_backfill` (bro only) recovers `agent_runs` from the Claude Code transcripts still under `~/.claude/projects/<project-slug>/` (or `transcripts_dir`), read-only. Each subagent transcript binds to a task by the hooks' rule (the first `task_id=<N>` in its message content, ported from `tmb_task_id_from_transcript`; a unit test runs both on the same fixtures) and is metered like the SubagentStop hook (usage per message id, cache read/write summed, dominant model); its agent is the spawn's `subagent_type` (the `.meta.json` beside it, else the parent session's Agent call), swe or pr-reviewer. It fills the row keyed `(task_id, spawn_id)` — `spawn_id` is the transcript path, a row keyed by the agent id counts as the same spawn — or the unkeyed row `task_brief` opened inside the spawn, else inserts one; a row a meter already wrote (`transcript`, `subagent_stop`, `backfill`) is skipped. Bro rows are left alone: the `bro-turn-usage` Stop hook meters bro per session. `dry_run` (default true) only reports; a real run writes in one transaction with one `agent_runs_backfilled` audit row.

`validation_record` (pr-reviewer only) derives who the reviewer was instead of trusting the caller. The `reviewer-identity-observe` PreToolUse hook records a `reviewer_identity_observed` audit row (`from_node` `hook:reviewer-identity-observe`) with the payload's `session_id` and `agent_id` when a pr-reviewer subagent calls the tool; in one transaction the handler takes the newest unconsumed row for `(task_id, attempt_n)` observed within `REVIEWER_OBSERVATION_TTL_S` (600 s), stamps `subagent_session_id` and `reviewer_agent_id` from it, marks it consumed and marks every older unconsumed row for the same pair superseded (`superseded_by` = the consumed row's id). A caller-supplied `subagent_session_id` is ignored. No row → `subagent_session_unavailable`, except on the honor-system path (`mcp_available: false`), which records the caller's `subagent_session_id`, leaves `reviewer_agent_id` NULL and writes `validation_session_unverified`. A newest row older than the TTL is never consumed: the call fails `subagent_session_unavailable` naming its age, and the re-call gets a fresh row from the hook. The honor-system path never overwrites a verified (`mcp_available = 1`) row (`verified_verdict_exists`); a verified call may replace a verified row. The observed `agent_id` must match `[A-Za-z0-9_-]{8,64}` (`reviewer_agent_id_malformed`) and must not be empty or any swe `agent_runs.spawn_id` of the task (`reviewer_not_independent`). `audit_append` refuses `reviewer_identity_observed` (`audit_event_not_writable_by_role`: its only writer is `hook`), so only the hook writes it. `task_provision` and `task_create_batch` refuse `issue_id = -1` (`system_issue_reserved`): the system issue carries audit rows only.

`task_reopen` and `task_update_spec` (bro only) change a task after provision. `task_reopen` moves a `closed` / `failed` / `escalated` / `running` task to `running`, appends `files_add` / `verification_add` to its fences, writes a `decision` discussion + `task_reopened` audit row, and recreates the worktree when missing (the same idempotent setup `task_provision` uses); it refuses a task whose issue is closed. `task_update_spec` replaces `files` / `verification` / `spec_body` of a `pending` / `running` / `needs_validation` / `completed` task with a `decision` discussion + `task_spec_amended` audit row carrying the old→new summary; the scope fence and verification gate read the new values from the DB on their next run.
