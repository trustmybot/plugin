# src/tools

The MCP tool modules for the trajectory server — one TypeScript file per domain. Each module exports a factory (e.g. `issueTools(db)`) returning `{ definitions, handlers }`: the JSON-Schema tool definitions Claude sees and the handlers that run against the SQLite trajectory DB. `index.ts` wires every module's definitions + handlers together and decorates each with the `agent` param used for role-gating.

It writes nothing outside the project. `onboard-sandbox.ts` writes or removes Claude Code's Bash sandbox block in the same file (`sandbox_enforcement`, default no): the filesystem `allowWrite` paths and the network `allowedDomains` TMB's remote commands need. When either writer creates `settings.local.json` in a git work tree that does not ignore it, `ensureLocalSettingsIgnored` (`onboard-sandbox.ts`) appends `.claude/settings.local.json` to the project's `.gitignore`; the sandbox result reports it as `gitignore_appended`. `onboard-scan.ts` is the `/onboard` pre-scan behind `onboard_state_get`'s `scan` key: offline git evidence per `repos` row (long-lived branches, `origin/HEAD`, first-parent merge counts, CI files, `CONTRIBUTING.md`), a branching recommendation with a confidence level, and a workspace summary, persisted in `repos.onboard_scan`; it never spawns gh/glab. `agent-runs.ts` opens and closes `agent_runs` rows with their `root_dir`, `host` and `exit_reason`; `containment.ts` holds the `outside_project` check the path-taking tools share. `lifecycle.ts` holds the issue/task lifecycle rules `issue_close`, `bro_atomic_close`, `task_recover` and `task_update_status` share: the live-task set, the passing-review rule behind `review_gate_bypassed` / `tasks_without_review`, the `issue_close` cascade, and the stale-running sweep.

Remote issue close: when `issue_close`, `bro_atomic_close` or `task_recover` closes an issue that is linked to GitHub/GitLab (`gh_iid` / `gl_iid`), it closes the remote twin only if `remoteSyncGate` (`sync/backend.ts`) is on — `TMB_DISABLE_REMOTE_SYNC` unset, `plugin_config.issue_sync` not `off`, and a usable gh/glab for the issue repo's remotes. The result carries `remote: {synced, skipped?, remotes: [{remote_kind, remote_iid, closed, skipped?}]}` (on `bro_atomic_close` / `task_recover` only when the issue closed): a linked remote whose provider has no `sync = 1` row is not spawned and carries `skipped: 'not_synced'`, and every linked remote of an issue whose repo resolves to no `repos` row carries `skipped: 'repo_unresolved'`; `synced` is true when at least one synced remote was attempted and every one of them closed; the top-level `skipped` is `issue_sync_off`, `env_disabled` or `no_backend` when the gate was off, in which case nothing was spawned and one `issue_close_remote_skipped` audit row records the reason. An issue with no remote link returns `{synced: false, remotes: []}`. `issue_sync_retry` returns `{skipped: true, reason: 'not_synced'}` when none of the issue's backends has a sync row.

Remote → DB reconcile (GH 2228): `issue_reconcile_remote` (bro, optional `dry_run`) runs `reconcileRemoteCloses` (`../sync/issue-reconcile.ts`), the one inbound path besides `close-issue-on-merge`. Behind the same `remoteSyncGate` (off → `{skipped: <reason>}`, nothing read or written), it reads every open issue with `id > 0` and a `gh_iid` / `gl_iid` from its repo's synced remotes: one `gh api graphql` call per repo and batch of 50 issue numbers, one `glab issue view --output json` per GitLab issue. An issue whose linked remotes all report closed and that has no live task closes (`markIssueClosed` + one `issue_closed_from_remote` audit row, one transaction); one with live tasks stays open, is listed in `deferred`, and gets an `issue_remote_closed_local_open` row whenever its blocking task set changes (the `issues_open_after_remote_close` doctor contract counts them). A read failure, a missing remote issue or an unsynced provider is an `errors[]` entry and closes nothing. It never writes to the remote. Returns `{checked, closed: [{issue_id, remote_kind, remote_iid}], deferred: [{issue_id, blocking_task_ids}], errors, skipped?, prs}`.

The same call then runs `syncRemotePrs` (`../sync/pr-sync.ts`, GH 2513), behind the same gate, for every repo with a synced GitHub remote: one `gh pr list -R <slug> --state all --json number,state,createdAt,mergedAt,updatedAt,closingIssuesReferences` per repo, `--limit 5000` while the repo has no `prs` rows, then `--limit 1000 --search "updated:>=<newest updated_at date> sort:updated-asc"`. Each PR upserts its `prs` row (`state` open/closed/merged, `merged_at` only when merged) and replaces its `pr_closes` rows with its same-repo closing issue numbers (references to another repository are skipped), one transaction per repo. A failed or unparseable read is an `errors[]` entry and leaves that repo's rows untouched; a page that hits its limit adds a `truncated` entry. `dry_run` reads and counts but writes nothing. `gh pr list` is the only command it spawns. `prs` is `{repos, upserted, errors: [{repo, reason, message?}], skipped?, dry_run?}`; the dashboard's PR merge tiles read these rows.

`milestone_close` closes the milestone on each synced remote and returns `remote_results: [{backend, slug, status, reason?, message?}]` (also in the `milestone_closed` audit content): `status` is `closed`, `skipped` (the remote has no such milestone, `not_found`) or `failed`. `remote_closed` is true when the gate was on, at least one target ran and none failed; `_sync` appears only on a failure, its hint naming the failed hosts.

## How it fits

`task_brief` returns the task's typed `verification[]` commands and `verification_run`: the latest run of them the close gate recorded (`{run_id, commit_sha, source, started_at, finished_at, exit_code, timed_out, budget_s, commands: [{ordinal, command, exit_code, elapsed_s}]}`, null when none), so bro and code-reviewer read the result instead of running the commands again. `validation_history` rows carry the same shape as `verification_run` — the latest run started by the attempt's `created_at`. The shared reader is `verification-runs.ts`.

`task_brief`'s `task_discussions` (GH 1741) holds this task's `decision` / `intent` rows in full (`discussions.task_id` = the task), the issue's newest issue-level decision (`task_id IS NULL`), the issue's newest issue-level intent (GH 1760: the Human's verbatim words `intent_start` records, truncated to 500 chars and not counted among the 8 other rows), and its last 8 other-kind rows truncated to 500 chars; a row another row names in `supersedes` is skipped. When rows are left out, `task_discussions_omitted` gives their count and points to `discussion_search(issue_id=N)` for the full history. Rows written before v46 have no `task_id`, so an old issue's brief carries only its newest issue-level decision and intent. That is the `detailed` output (GH 1958): by default `response_format` is `concise`, which reduces the other-kind rows to `id`, `kind` and `author`, drops `summary` from `scope_world_model`, and adds `response_format_hint` when it trimmed anything.

These modules are the entire MCP surface bro and the subagents call. `index.ts` is the registration point and wraps every handler in `requireAgent()`, so a call with a missing or invalid `agent` fails on every tool with `error: missing_argument`, `argument: agent` and `reason: agent_missing_or_invalid` (a known role a tool does not admit gets `error: forbidden` with `caller_role`); role-gating per tool is enforced by `requireRoles()` in `../middleware/agent-scope.ts`. `normalizeAgent` strips a leading `tmb:` (Claude Code's subagent namespace), so `tmb:swe` is `swe` and `tmb:pm` is a consultant. Read-only tools (`world_model_get`, `world_model_search`, `world_model_symbol`, `world_model_concepts`, `world_model_concept_get`, `repos_list`, `task_brief`, `issue_snapshot_md`) admit consultants; write tools keep their narrower lists. See `../../README.md` for the tool-family overview, environment, and schema notes. Handlers are unit-tested at L2 (`../test/`).

## Discussions: single insert+embed path

Every discussion write — `discussion_append` plus every composite that logs an `intent` / `decision` / `note` (`task_provision`, `intent_start`, `task_retry`, `task_reopen`, `task_update_spec`, `bro_verification_fail_record`) — goes through one helper, `insertDiscussion(db, { issue_id, author, kind, body, created_at?, repo?, remote_comment_id?, task_id?, supersedes? })` in `discussions.ts`. `task_provision`, `task_retry`, `task_reopen` and `task_update_spec` set `task_id` on the decision they write; `discussion_append` takes optional `task_id` and `supersedes`, each checked to belong to the same issue, except that a `note` or `analysis` row may name a task on another issue (GH 1869: world-model feedback rows live on the feedback issue but name tasks from many issues); a nonexistent task is refused for every kind. It INSERTs the row and fires `embedAndStore` so the entry is indexed for semantic `discussion_search`. The embed is not awaited and its failure is caught (degrades to FTS-only), so when a composite calls it inside `db.transaction()` the embedding write lands after COMMIT and an embed failure never rolls back the transaction. No module writes the `discussions` table directly. `pr_monitor_comments_get` persists each fetched PR/MR comment through it with `remote_comment_id = '<provider>:<pr_number>:<comment_id>'`; on that key the INSERT is `ON CONFLICT DO NOTHING` against the partial UNIQUE index, so an already-stored comment returns null and is neither inserted nor embedded. The tool result is the fetch payload (`comments`, `pr_state`, `remote_kind`, `head_branch`) plus `persisted` (new rows) and `duplicates` (comments already stored); the carrier is the issue of the PR's task (`pr_review_runs.task_id`, else the most recently updated task on the head branch), closed tasks included and failed or escalated ones skipped. When the PR's slug maps to a registered repo, only that repo's tasks (and legacy tasks with no repo) qualify; when it maps to none, the newest-updated matching task across all repos wins. Both counts are 0 when no task carries the PR.

## Audit: who may write which event

Every audit row goes through `insertAudit` (`audit.ts`). Each event in `../audit-events.ts` lists its `writers` — the agent roles that may author it, `server`, or `hook`. `audit_append` takes the role from the `agent` arg (the same `normalizeAgent` path `requireRoles` uses), refuses an event whose writers omit that role with `audit_event_not_writable_by_role` (`event_type`, `caller_role`, `allowed_writers`), and records `from_node` as the caller itself — `bro`, `swe`, `code-reviewer`, or a consultant's name; a `from_node` arg naming anyone else is refused. `insertAudit` runs the same check when given `writer`. So no agent but bro can write a gate waiver (`verification_gate_waived` is hook-only), and `GATE_SKIP_RECORDED_SQL` (`../review-sql.ts`) counts a review waiver only when `from_node = 'bro'`.

## Atomicity notes

`task_provision` is atomic from the caller's view: it resolves the repo path, then runs the environment gate (`env-gate.ts`, GH 2866) **before** committing the decision + task transaction. The gate's stages run in order: fetch (`git fetch origin <base>` when the repo has an `origin` remote, else skipped), branch (cut or reuse the ref, below), worktree, setup (`.config/tmb/worktree-setup.json`, skipped when absent) and reindex (passes only when the world model is indexed at the base commit; skipped, with `wm_commit` null and a line in the decision body, when the server has no world-model graph). A failed stage returns `env_gate_failed` (`stage`, `detail`, `output_tail?`) and persists nothing, removing the branch and worktree this call created and never a reused one — no orphan task row is left occupying the `(issue_id, branch_id)` UNIQUE constraint, so the same `branch_id` retries cleanly once the cause is fixed. A pass returns `env_gate.stages`, and the task records `base_sha` (the commit the worktree was cut from) and `wm_commit`. Only an adopted worktree (`adopt_worktree`, below) skips the gate and is switched after the commit, fail-soft into `git_setup:'error'` with a diagnostic. `git_setup:'created'` means a new ref from `base`; an existing local or origin ref at or behind the base tip is fast-forwarded and reported `'reused'`; a diverged ref is refused with `branch_exists_diverged` (ref, ahead/behind distance, open PRs read with `gh pr list --head` / `glab mr list --source-branch` under the issue-sync gate) unless `reuse_existing: true` keeps it as-is (`'reused'`). `worktree_reused` reports an existing worktree separately. A `branch_id` the issue already has a task on is refused before any git call with `branch_id_used_on_issue` (the existing `task_id`, `status` and `commit_sha`, naming `task_reopen`, a new name from `branch_id_propose`, or `task_provision` with `base='<branch_id>'` to stack on it as the next step), with or without `reuse_existing`; `task_retry` refuses such a `new_branch_id` the same way.

`agent_register`, `agent_list` and `agent_resolve` speak one `file_path` shape: `plugin:<path>` (relative to the installed plugin root, resolved via `resolvePluginRoot()`) or `project:<path>` (relative to the workspace root derived from the DB path); an unmarked path is refused with `invalid_file_path`. Every returned agent row carries the absolute `resolved_path` (null for a `project:` path when the DB is `:memory:`). `swe` and `code-reviewer` must be `plugin:` — a `project:` registration under those names would shadow the backbone and is refused. `agent_register` with a `project:` path promotes a `plugin:` consultant row and audits `tmb_agent_created`; `agent_list` filters by `root` (`plugin` / `project`); `agent_resolve` (bro only) takes an optional target `file_path` (default `project:.claude/agents/<name>.md`) and returns it with its `resolved_path` and the creation mode.

`agent_runs_backfill` (bro only) recovers `agent_runs` from the Claude Code transcripts still under `~/.claude/projects/<project-slug>/` (or `transcripts_dir`), read-only. Each subagent transcript binds to a task by the hooks' rule (the first `task_id=<N>` in its message content, ported from `tmb_task_id_from_transcript`; a unit test runs both on the same fixtures) and is metered like the SubagentStop hook (usage per message id, cache read/write summed, dominant model); its agent is the spawn's `subagent_type` (the `.meta.json` beside it, else the parent session's Agent call), swe or code-reviewer. It fills the row keyed `(task_id, spawn_id)` — `spawn_id` is the transcript path, a row keyed by the agent id counts as the same spawn — or the unkeyed row `task_brief` opened inside the spawn, else inserts one; a row a meter already wrote (`transcript`, `subagent_stop`, `backfill`) is skipped. Bro rows are left alone: the `bro-turn-usage` Stop hook meters bro per session. `dry_run` (default true) only reports; a real run writes in one transaction with one `agent_runs_backfilled` audit row.

`validation_record` (code-reviewer only) derives who the reviewer was instead of trusting the caller. The `reviewer-identity-observe` PreToolUse hook records a `reviewer_identity_observed` audit row (`from_node` `hook:reviewer-identity-observe`) with the payload's `session_id` and `agent_id` when a code-reviewer subagent calls the tool; in one transaction the handler takes the newest unconsumed row for `(task_id, attempt_n)` observed within `REVIEWER_OBSERVATION_TTL_S` (600 s), stamps `subagent_session_id` and `reviewer_agent_id` from it, marks it consumed and marks every older unconsumed row for the same pair superseded (`superseded_by` = the consumed row's id). A caller-supplied `subagent_session_id` is ignored. No row → `subagent_session_unavailable`, except on the honor-system path (`mcp_available: false`), which records the caller's `subagent_session_id`, leaves `reviewer_agent_id` NULL and writes `validation_session_unverified`. A newest row older than the TTL is never consumed: the call fails `subagent_session_unavailable` naming its age, and the re-call gets a fresh row from the hook. No call overwrites a row (GH 2412): an `attempt_n` that already has one is stored as the task's highest `attempt_n` + 1, and the result names the stored attempt. The observed `agent_id` must match `[A-Za-z0-9_-]{8,64}` (`reviewer_agent_id_malformed`) and must not be empty or any swe `agent_runs.spawn_id` of the task (`reviewer_not_independent`). `audit_append` refuses `reviewer_identity_observed` (`audit_event_not_writable_by_role`: its only writer is `hook`), so only the hook writes it. The row also gets `reviewed_sha` (GH 2684): the `commit_sha` of the newest `reviewer_spawn_observed` audit row (`from_node` `hook:record-reviewer-spawn`, written by the last PREPARE step of `agent-spawn-dispatch` when it allows a code-reviewer spawn) for the caller's `(task_id, attempt_n)`, with no freshness window, and NULL when no spawn was observed. It is the commit the review covered, which can differ from `tasks.commit_sha` once a merge moves the task's commit; `validation_history` returns it and admits it in `fields`. `task_provision` and `task_create_batch` refuse `issue_id = -1` (`system_issue_reserved`): the system issue carries audit rows only.

`wm_feedback` (GH 2417) is the world model's feedback loop: swe's `task_update_status(status='completed')` report and code-reviewer's `validation_record` each take an optional `wm_feedback` `{answered?, missed?, wrong?}`, the strings saying what the world model answered, missed or got wrong during the task. `wmFeedbackProblem` (`../success-criteria.ts`) refuses a non-object, an unknown key or a non-string value (`completion_report_invalid` on the report, `wm_feedback_invalid` on `validation_record`), and `insertWmFeedback` (`validation.ts`) writes one `wm_feedback` audit row on the task's issue in the same transaction as the status or validation row, and none when `answered`, `missed` and `wrong` are all absent or blank. `task_update_status` admits `report.wm_feedback` only from swe and refuses any other agent with `wm_feedback_invalid` before it writes anything, so a row's writer is always swe or code-reviewer. Swe's copy also stays in `tasks.completion_report`, blank or not. `trajectory_doctor` returns `wm_feedback` `{reports, missed, wrong}` counted from those rows.

`task_reopen` and `task_update_spec` (bro only) change a task after provision. `task_reopen` moves a `closed` / `failed` / `escalated` / `running` task to `running`, appends `files_add` / `verification_add` to its fences, writes a `decision` discussion + `task_reopened` audit row, and runs `task_provision`'s environment gate first, which recreates the worktree when missing; a branch missing both locally and on origin is first cut from the task's base (`branch_created: true`). A failed stage refuses with `env_gate_failed` and leaves the task's status, fences and rows as they were. It refuses a task whose issue is closed, and an explicit `effort` below `high` while the task has a review FAIL since its last pass (`effort_below_rework_floor`). A code-reviewer `fail` verdict reopens the task without bro (GH 2866): in the transaction of the FAIL row, `validation_record` moves a `completed` / `needs_validation` / `closed` task of an open issue to `running` at effort `high`, clears `completion_report`, sets a spawn note naming the blocking finding ids with their class, and writes a `decision` discussion, a `task_reopened` audit row (`from_node` `code-reviewer`, with `validation_id`, `finding_ids` and `auto: true`) and a `task_effort_raised` row when the effort was below `high`; it skips the environment gate, so a lost worktree is recreated by a later `task_reopen`. A `running` task only gets its effort raised to `high`; a `pending`, `failed` or `escalated` task, or one of a closed issue, is left as it is. The result carries `reopened: {task_id, from_status, status, effort, effort_raised, finding_ids}` or `reopen_skipped: {reason}`, and `return_line` is unchanged. The `task_reopened` row also keeps the cleared `completion_report` and `completed_at`, for a re-review of a disputed FAIL: `review_handoff` re-hands a `running` task's commit to a new code-reviewer only when the task's latest verdict is a FAIL on that same commit, no swe run of the task is live, a passing verification run is recorded for the commit, and the task's latest `task_rework_analysis`, dated after the FAIL, names `re_review`. It then restores `completed` with that report and stamp, and records `re_review_of` (the FAIL's validation id) on its `review_handoff` row and result; any other running task is refused with `re_review_refused`, naming the first unmet condition. The handoff's usual checks still apply, so a disputed blocking finding needs its probe to pass or a `wontfix`. Its optional `wontfix: [{finding_id, reason}]` records review findings the Human accepts: each entry must name an open finding of the task once, with a reason of at least 10 characters, or the whole call is refused and nothing is written; each finding becomes `wontfix` with `resolved_at` set inside the reopen transaction, gets one `review_finding_wontfix` audit row carrying the reason, drops out of `task_brief.open_findings` and is no longer probed by the close gate; the result lists the ids in `wontfixed`. `task_retry` copies the failed task's open blocking findings onto the new task in id order, in its transaction: each copy keeps `criterion_id`, `probe_cmd`, `expected`, `observed`, `severity` and `class`, and gets id `F<new_task_id>-<n>`, `attempt_n` 0 (so the retry's reviewer attempts, from 1, never replace it) and status `open`; the failed task's rows stay as they are, one `review_findings_carried` audit row maps old to new ids, and the result carries `carried_findings: [{from, id}]`. `task_retry` cuts `new_branch_id` with `task_provision`'s branch policy (base: the failed task's `parent_branch_id` when it resolves, else the repo target branch, else the default branch) in the environment gate before its transaction, so an unresolvable base, a diverged existing ref or any other failed stage returns `env_gate_failed` and inserts no task; the result carries `git_setup`, `base_ref`, `base_sha`, `wm_commit`, `env_gate` and `worktree_path`. `task_update_spec` replaces `files` / `verification` / `spec_body` of a `pending` / `running` / `needs_validation` / `completed` task with a `decision` discussion + `task_spec_amended` audit row carrying the old→new summary; the scope fence and verification gate read the new values from the DB on their next run.

`task_rework_analysis` (bro only, GH 2830) records bro's analysis of a task's review FAILs since its latest pass as one `task_rework_analysis` audit row on the task's issue, carrying every argument, and returns `{audit_id, task_id}`. `fail_validation_ids` must each be a `fail` `validation_attempts` row of the task after its latest pass and must include the latest FAIL; `finding_ids` (at least one) must match `F<task_id>-<n>`; `root_cause` is one of `spec_unclear`, `spec_wrong`, `world_model`, `reviewer_disputed`, `environment`, `swe_execution`, `design_drift`; `change` one of `spec_update`, `world_model_fix`, `effort_raise`, `split`, `retry`, `re_review`, `ask_human`; `approach_shared_cause` a boolean saying whether the findings share one cause in the approach itself; `rationale` at least 20 characters. `world_model` takes only `world_model_fix`, `design_drift` only `split` or `retry` (GH 2857), and `approach_shared_cause: true` takes only `split` or `retry`; `ask_human` pairs with any other cause and admits no swe run. Any other value or pairing is refused with `rework_analysis_invalid` and writes nothing. The `rework-limit` gate reads the row (see `scripts/hooks/README.md`).

`verification-paths.ts` (GH 2581, FLOWS guard G15) is the test-path guard `task_provision`, `task_retry`, `task_reopen` and `task_update_spec` (when it gets `files` or `verification`) run before they write. `checkVerificationPaths` first runs `checkVerificationProse` (GH 2955; the two writers whose ref may not resolve call it directly then): an entry is refused with `verification_not_command` when the first command word of any of its simple commands (split at `&&`, `||`, `;`, `|`; env assignments and prefix words skipped; `bash -c` read as its own command) matches `^[A-Z][a-z]+$` and is not a `/` path, a shell builtin or an executable listed by exact name in a PATH dir, as `{error, message, ref, missing: [{command, path, reason}]}` with `path` the offending word; a lower-case word is never refused for being missing from PATH. It then finds the test files the `verification[]` commands hand a test runner (`*.test.{ts,mts,js,mjs,cjs}`, `*.spec.*`, `*.suite.ts`, `test_*.py` as a file argument of `node`, `bun test`, `vitest`/`jest`/`mocha` bare or via `npx`/`bunx`/`pnpm exec`, or `pytest`/`python -m pytest`; `bash -c '<cmd>'` is parsed as its own command; a `cd <dir>` at any step sets the directory later steps resolve under, until the close of its `( … )` subshell; words of any other program, env assignments and git pathspecs are never checked) and admits each only when `files[]` lists it verbatim or git proves it at the ref (`git cat-file -e`, or `git ls-tree` with at least one match for a glob); an untracked `dist/**/*.js` is checked as its `src/**/*.ts`. The ref is the cut base for provision and retry (checked before the branch is cut) and the task branch tip for reopen and update_spec. A miss is refused with `verification_path_missing`, and a git error, an unresolvable ref or no repo path with `verification_path_unverified`, each as `{error, message, ref, missing: [{command, path, checked_as?, reason}]}`, and nothing is written. `suggestVerification` adds `suggested_verification` to all four results: up to 20 `{test_path, imports, source: 'world_model.imports'}` entries for existing tests whose module imports a `files[]` module (`wm_edges` kind `imports`), leaving out tests `verification[]` already names; with no world model rows for the repo it is `[]` with a `suggested_verification_note`. Suggestions never block and are never added to `verification[]`.

`verification-defaults.ts` (GH 2570) adds the repo's own default checks to every new task. A repo commits `.config/tmb/verification-defaults.json`, `{"version":1,"commands":["..."]}` with each command a non-empty string (the plugin repo's runs `node --experimental-strip-types tests/run-all.ts --l1-local`). `task_provision` and `task_retry` read it with `git show <ref>:.config/tmb/verification-defaults.json` at the same ref the test-path guard checks, before that guard runs, so a default's test paths are checked too; a copy only in a worktree or an uncommitted edit never counts. They store `verification[]` as the task's own commands followed by each default not already listed verbatim, in file order, and return the appended ones in `verification_defaults_added` (`[]` when none). No file at the ref, no ref or no repo path adds nothing. A file that is not JSON, not version 1 or has no non-empty string array `commands`, or a git error reading it, is refused with `{error: 'verification_defaults_invalid', message, ref, file}` and nothing is written: no task row, branch or worktree. `task_reopen` and `task_update_spec` (GH 2866) read the file at the ref `task_retry` would cut that task from (its parent branch, else the repo's target branch, else its default branch), append each default the task's `verification[]` lacks after `verification_add` or the replacement list, and return `verification_defaults_added` the same way; on `task_update_spec` an appended default counts as a `verification` change. A file they cannot read or parse refuses the call before anything is written.

`task_provision`, `task_reopen` and `task_retry` take an optional `adopt_worktree` (GH 2032): the absolute path of the linked git worktree bro's session runs in. The task then works in that worktree instead of `<repo>/.claude/worktrees/<slug>`, which is never created. Before any write, and for provision and retry before the branch is cut, `adoptWorktreeCheck` refuses with a typed `{error, message, task_id?}` and writes nothing (no task row, discussion, audit row or branch ref; a refused `task_reopen` leaves the task's status and fences as they were): `adopt_worktree_repo_mismatch` (not the top level of a linked worktree of the task's repo), `adopt_worktree_main_checkout`, `adopt_worktree_dirty` (tracked changes; untracked files pass) and `worktree_in_use` (a live task other than this one records it, or holds it as its slug worktree; `task_id` names it). Otherwise the tool's transaction records the realpath as `tasks.worktree_path` with `worktree_adopted = 1` (the holder is checked again there; a late holder rolls the transaction back with the same refusal), then `git switch`es the worktree to the task branch; a failed switch keeps the record and returns a `diagnostic`. The result's `worktree_path` is the adopted realpath and `worktree_adopted` is `true`. `adoptTaskWorktree` is the same path for an existing task, behind `ADOPT_WORKTREE_ENABLED` (on). Which worktree a session may pass is decided by the `worktree-adopt-guard` PreToolUse hook, not the server: from a linked worktree the argument is required and must name it, from anywhere else it is refused.
