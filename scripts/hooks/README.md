# scripts/hooks

The Claude Code lifecycle hook engine — the deterministic enforcement layer that gates, nudges, and reacts to what bro and the subagents do each session. Every script reads a hook JSON payload on stdin and either exits silently, emits `additionalContext`, or returns a `permissionDecision: deny`. The wiring (which script runs on which event) lives in the plugin-root `hooks/hooks.json`; the scripts here are the implementations.

## `dispatch.sh` — the one entry point

Every `hooks/hooks.json` command is `${CLAUDE_PLUGIN_ROOT}/scripts/hooks/dispatch.sh <gate>` (timeout = the gate's budget + 1 s), and the opt-in headless shim execs `dispatch.sh <gate> --shim`. The dispatcher:

1. runs the gate of the install this project uses — `lib/resolve-install.sh` picks it from `installed_plugins.json` (project/local beats user, newest of two project installs, no entry → the invoking plugin root) — with `CLAUDE_PLUGIN_ROOT` pointing at that install;
2. with `--shim`, exits 0 without running the gate for another project's session or a session the plugin's own hooks already cover (the `plugin-hooks-marker.sh` marker);
3. runs the gate once per (event, payload, gate): a `mkdir` lock at `<project>/.claude/<plugin>/locks/events/<sha256>/` holds the gate's `result`, `stderr` and `rc`; a concurrent duplicate replays only a denial and otherwise exits 0 silently. A finished result answers duplicates for `TMB_DISPATCH_WINDOW_S` (default 5 s); results are pruned after `TMB_DISPATCH_TTL_MIN` (default 10 min); a lock whose holder died is reclaimed once it is older than the gate's timeout. The lock directory and the shim's project comparison use the project's physical path (`cd -P`), so a symlinked project dir and its real path share one lock. A project with no trajectory DB gets no lock — the gate just runs.

`tests/l1-lint/hooks-via-dispatcher.sh` keeps every registration on the dispatcher; `tests/l3-integration/hooks/dispatch.test.sh` covers dedup, install resolution and the shim yield. The rule is written up in [`docs/architecture/CONTAINMENT.md`](../../docs/architecture/CONTAINMENT.md).

## Grouped by lifecycle

### SessionStart — preflight
`ensure-gitignore.sh`, `mcp-health-check.sh`, `deferred-tools-drift-warn.sh`, `plugin-hooks-marker.sh`, `session-start-prescan.sh`, `ensure-kuzu-installed.sh`, `substrate-preflight.sh`, `cheatcode-healthcheck.sh`, `orphan-scan.sh` — make sure the gitignore, MCP server, kuzu native binary, and required host binaries are in place before a session does real work, mark the session as running the plugin's own hooks (so the opt-in headless shim yields), warn about TMB-managed hooks left in `~/.claude/settings.json`, say once per session when a user-scope install is ignored for the project's (or recommend `--scope project` when only a user-scope install exists), and reconcile cheatcode statuses.

Every file a hook writes lives under `<project>/.claude/<plugin>/` (logs, locks, session markers); nothing is written under `$HOME` (`tests/l1-lint/no-home-writes.sh`).

#### `orphan-scan.sh` — project-scoped cross-upgrade orphan scan

Detects (and, only when explicitly opted in, cleans) TMB artifacts left behind by version upgrades. Advisory: it emits findings as `additionalContext`, soft-fails, caps itself with a tight internal timeout, and never blocks session start.

**Project-scoping invariant (load-bearing).** A user may run a *different* TMB version in *other* projects — each with its own cache dir, MCP process, and `trajectory.db`. Those are legitimate, not orphans. The hook resolves the current project first (session cwd / `CLAUDE_PROJECT_DIR` → its `.claude/<plugin>/trajectory.db` live path and its `~/.claude/projects/<this-slug>/` history dir) and confines all detection and cleanup to it. It never enumerates, reports, or touches another project's DB, process, or pinned cache version. The single permitted cross-project action is removing a cache version that *no* `installed_plugins.json` entry pins (globally unused).

What it detects, current project only:
1. **Stale old-layout DBs of this project** — `~/.claude/projects/<this-slug>/trajectory.db`, its `memory/trajectory.db`, and a legacy `~/.claude/<plugin>/trajectory.db` only when this project has no live DB yet. A candidate is 0-byte *or* has a `schema_version` older than the live DB. The live `<project>/.claude/<plugin>/trajectory.db` is always kept.
2. **Stale duplicate MCP proc on this project's live DB** — a second `trajectory-server` node proc holding *this* project's live DB (the lowest PID is kept as the live server). A proc holding any other project's DB is never flagged. `lsof` absence degrades gracefully.
3. **Globally-unused cache versions** — a `~/.claude/plugins/cache/<channel>/<plugin>/<version>` dir referenced by no `installed_plugins.json` entry. A version pinned by any project (current or other) is never a candidate.

**Safety gates.** Detection-first: the default mode reports only and deletes nothing. Cleanup is gated behind `TMB_ORPHAN_SCAN_CLEAN=1` (default OFF) and is limited to this project's provably-dead stale DBs, a confirmed stale duplicate proc on this project's live DB (with a `kill -0` liveness check), and globally-unused cache versions. It never removes the live DB, never touches another project's DB / proc / cache, and never removes a pinned version. The scan is idempotent and soft-fails. (Tests set `TMB_ORPHAN_SCAN_HOME` / `TMB_ORPHAN_SCAN_PROJECT_DIR` to sandbox HOME and project-root resolution.)

#### `cheatcode-healthcheck.sh` — cheatcode status reconciliation

Sets each `cheatcodes` row's `status` to `active` or `broken` from runtime evidence and writes a `cheatcode_healthcheck` audit row per change. Names always match exactly, never as a substring (`tmb` never matches `tmb-x`):
- `skill` — `file_path` exists on disk.
- `mcp` with `source_url` `mcp:<plugin>/<server>` (a plugin-bundled server, as `/scan` records it) — `claude plugin list --json` has an entry whose `id` before `@` is `<plugin>`, it is `enabled`, and its `mcpServers` has the key `<server>`.
- any other `mcp` row — the name is a server name in `claude mcp list` or a `~/.claude.json` `mcpServers` key.
- `plugin` — `claude plugin list --json` has an enabled entry whose `id` before `@` is the name.

A row whose evidence source is unavailable (no `claude` CLI, an unparseable plugin list, no MCP listing) is left untouched. Bypass: `TMB_DISABLE_CHEATCODE_HEALTHCHECK=1`.

### UserPromptSubmit — per-turn setup + routing
`activation-routine.sh`, `session-log-capture.sh`, `prompt-intent-hints.sh`, `roundtable-slash-detect.sh` — inject identity/context (plus the HALT + recovery pointer when the trajectory-server is not running at the prompt, and `session_id=<id>` for bro's planning calls), log the turn, and route phrasing hints (onboarding nudges, roundtable detection). Harness turns — task/system notifications, subagent hand-backs, agent and cross-session messages — never fire a hint, record `/roundtable`, or activate bro mode by mentioning bro; hints match only the prompt's unquoted text.

### PreToolUse — gates (deny on violation)
Git: `git-guards.sh`, `git-push-guard.sh`, `no-remote-auth-guard.sh`, `stay-on-base-guard.sh`, `no-source-edit-from-main.sh`, `no-worktree-branch-create.sh`, `branch-up-to-date-with-remote.sh`, `commit-msg-lint.sh`. Every Bash gate judges the command's executable statements only (`tmb_cmd_statements`): text inside heredoc bodies and quotes is data. Each statement runs in its effective dir — its `git -C <path>`, else a preceding `cd <path>`, else the payload cwd when that cwd belongs to a single checkout; when the repo has linked worktrees and the statement names no dir, a gate that needs its branch denies with `ambiguous_git_target` and the remedy (`git -C <path>` or `cd <path> && …`). The agent's role comes from its identity (`tmb_agent_role`), never from a path. The git guards are **registration-scoped**: they resolve each statement's git-root to a `repos` row (via `lib/resolve-repo.sh`) and only enforce on a registered repo — unregistered sibling trees no-op. The protected set is the Rule 2 union of `protected_branches`, `target_branch`, `pr_target`, and the parent branches of this repo's tasks. The first three are read per-repo from the `repos` row — the `repos` row is the source of truth, with no `plugin_config` fallback — and the last comes from the tasks table. On a detached-HEAD worktree the branch is the newest task whose `branch_id` ends in `/<worktree dir name>` (`tmb_task_by_slug`). `git-push-guard.sh` gates a branch's first push (no upstream) on the commits past its target branch: the repo's `repos.target_branch`, else the sole registered repo's, else the remote's default branch (`origin/HEAD`), else `main`. See [`docs/architecture/REPO_RESOLUTION.md`](../../docs/architecture/REPO_RESOLUTION.md).
Agent dispatch: `agent-spawn-dispatch.sh`, `swe-brief-gate.sh`, `swe-verification-gate.sh`, `swe-boundary.sh`, `swe-scope-fence.sh`.
Containment: `containment-guard.sh` (Write/Edit/MultiEdit/NotebookEdit/Bash) denies a write outside the run's root — the open swe/pr-reviewer `agent_runs.root_dir` of the active task, else the project (`CLAUDE_PROJECT_DIR`). File tools are judged by the canonical `file_path` (symlinks followed before `..` applies, as the kernel resolves it); Bash by its `cwd` and every write position `lib/cmd-analysis.sh` finds after heredoc bodies and quoted text are neutralized, both ends of `ln`/`link`/`cp -s`/`cp -l` included. Writes under the model cache (`TMB_MODEL_CACHE_DIR`), the host's own temp dir (`$TMPDIR` and its realpath) and `/dev/null`-style devices are allowed; in the main session only (bro, never swe or pr-reviewer), so are Claude Code's own per-project dir `~/.claude/projects/<slug>/` and plans dir `~/.claude/plans/`. Reads are never judged. Each denial writes a `containment_denied` audit row. See [`docs/architecture/CONTAINMENT.md`](../../docs/architecture/CONTAINMENT.md).
AUQ / roundtable / cheatcode: `askuserquestion-length-lint.sh`, `roundtable-auq-shape.sh`, `cheatcode-install-approval.sh`.
Lint: `naming-lint.sh`, `code-quality-lint.sh`, `debug-trajectory.sh`.

### PostToolUse — reactions after a tool succeeds

### Stop / SubagentStop / WorktreeCreate
`bro-turn-usage.sh` (Stop), `swe-atomic-close.sh` + `consultant-persistence-gate.sh` (SubagentStop), `worktree-create.sh` (WorktreeCreate).

#### Metering — `agent_runs` by time window
Each `agent_runs` row covers `[started_at, completed_at)` of one agent's run on one task, and every token column is a per-message sum over the row's window (messages grouped by id, so content-block lines count once); the server opens and closes the rows (task creation / `task_brief` open them with `root_dir` and `host`, `bro_atomic_close`, a terminal `task_update_status` and `task_recover` close them with an `exit_reason`), the hooks only measure — tokens plus the run's dominant `model` (the transcript model with the most tokens in the window).
- `bro-turn-usage.sh` reads `session_id` + `transcript_path` from the Stop payload. Rows bro opened with `session_id` (passed to `task_provision` / `task_create_batch` / `task_retry`) are already its own; for legacy rows opened without it, it claims open (or recently closed) bro rows with no `session_id` that started after the session's first transcript message and writes one `agent_runs_claimed` audit row (`{run_ids, session_id}`) per claim. Then, in the same `tmb_db_write` transaction, it sets each of its own rows (open, or closed within 24 h) to the sum of the transcript's main-loop assistant usage inside the row's window (window start widened by 2 s), with `duration_ms` = the window length and `usage_source='transcript'`. Content-block lines of one message are counted once. Where windows overlap (a `task_create_batch` opens its rows at one instant), a message goes to the row whose task is running at the message's timestamp (status `running` set at or before it, or a swe row of the task open then), else to the row whose task was most recently briefed before it (`swe_brief_fetched`), else to the newest `started_at`. Recomputed absolutely on every Stop, so a re-run changes nothing and another session's rows are never touched. Bypass: `TMB_DISABLE_BRO_TURN_USAGE_HOOK=1`.
- `swe-atomic-close.sh` binds the spawn to `task_id=<N>` from its spawn prompt (`tmb_task_id_from_transcript` in `lib/query-task.sh`, which `swe-brief-gate.sh` shares) for a task in any status; with no id or no such task it writes an `agent_runs_capture_skipped` audit row and stops. It writes the spawn transcript's totals onto the swe row `task_brief` opened, keyed `(task_id, spawn_id)` with `spawn_id` = the payload's `agent_id`, or inserts a complete row; a re-fire updates in place. The row also takes `host`, the worktree as `root_dir` when unset, and an `exit_reason` from the task's state once the spawn ended (`completed` for completed/closed tasks, `escalated`, else `failed`). Only a `pending` task can be auto-completed; a SWE stopping while `running` or `failed` gets metrics only.

### Not wired in hooks.json
`require-task-spec.sh`, `require-feature-branch-active.sh`, `pr-reviewer-after-atomic-close.sh`, `pr-reviewer-no-worktree.sh`, `pr-reviewer-spawn-prompt-shape.sh` — PreToolUse-on-Agent guards (spawn-shape / spec / branch checks) not currently referenced by `hooks.json`.

## Subdirectory

- `lib/` — shared helpers sourced by the hook scripts (`cmd-analysis.sh`, `db-write.sh`, `normalize-role.sh`, `query-task.sh`, `resolve-install.sh`, `resolve-repo.sh`, `resolve-toolchain-path.sh`, `resolve-workspace.sh`). `query-task.sh` locates the trajectory DB and reads it (`tmb_db_path`, `tmb_gate_read`, `tmb_sql_int` / `tmb_sql_quote` / `tmb_sql_like_escape`) and resolves the task a worktree belongs to (`tmb_resolve_task_id_for_target`: the worktree's checked-out branch as an exact `branch_id`, else `tmb_task_by_slug` — `_` and `%` literal, newest of several with a stderr warning — else `task_id=<N>` in the spawn transcript). `resolve-install.sh` reads `installed_plugins.json` (read only; `TMB_INSTALLED_JSON` overrides the path) and prints the install this project uses (`tmb_active_install`). `cmd-analysis.sh` reads shell commands and prompts: `tmb_cmd_strip_literals` (heredoc bodies dropped, quoted operators neutralized), `tmb_cmd_write_targets` / `tmb_cmd_write_paths` (the paths a command writes), `tmb_cmd_statements` (statements with their effective dir), `tmb_git_subcommand`, `tmb_gh_mutation` (the forge write a gh/glab statement makes: a mutating subcommand or an api write verb, explicit in any flag position or implied by field parameters — so every `gh api graphql -f query=…` counts as a POST), `tmb_git_commit_message` (the first `-m` of the real argv), `tmb_stmt_repo_root`, `tmb_cwd_state`, `tmb_deny_ambiguous_git_target`, `tmb_agent_role` (the one source of role), `tmb_is_harness_turn`, `tmb_strip_quoted_spans` and `tmb_path_canonical`. `db-write.sh` is the only trajectory-DB write path: `tmb_db_write` (foreign keys on, 2 attempts of a `TMB_DB_WRITE_TIMEOUT_MS` busy wait — default 1500 ms, raised by hooks with a large hooks.json timeout — one transaction, failure reported on stderr), `tmb_audit_append` (audit rows as `from_node` `hook:<name>`), `tmb_now_iso` (the one timestamp format), and `tmb_gate_read` (prints `__ERR__` on a DB error so deny-capable gates fail closed).

## How it fits

Hooks are TMB's enforcement substrate: they make the workflow doctrine mechanical instead of advisory. A PreToolUse deny is a hard stop for the agent that tripped it. Hook behavior is covered by L3 (`tests/l3-integration/hooks/`).
