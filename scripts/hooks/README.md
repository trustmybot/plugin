# scripts/hooks

The Claude Code lifecycle hook engine — the deterministic enforcement layer that gates, nudges, and reacts to what bro and the subagents do each session. Every gate reads a hook JSON payload on stdin and either exits silently, emits `additionalContext`, or returns a `permissionDecision: deny`. The wiring (which gate runs on which event) lives in the plugin-root `hooks/hooks.json`; the gates are TypeScript, one `<gate>.ts` per gate in `mcp/trajectory-server/src/hooks/`. This directory keeps the gate docs below and, in `lib/`, the build-generated `audit-events.txt` and `data-contracts.json` the gates read at runtime.

## The router

Every `hooks/hooks.json` command is the TypeScript router, `node dist/hooks.js <Event> [part]`, one entry per matcher group, with the `${CLAUDE_PLUGIN_ROOT}` placeholder quoted, so a plugin root containing a space stays one word. The SessionStart default entry and the WorktreeCreate entry first run a POSIX guard, `command -v node >/dev/null 2>&1 || { echo '<TMB DEGRADED line>' >&2; exit 2; }; node …`, so with `node` off PATH they exit 2 naming the missing node instead of exiting 127 before substrate-preflight can (GH 2215); the fail-closed PreToolUse entries need no guard, since `onFailure: "block"` already denies when node can't start. The one exception is the Stop entry `node dist/hooks.js liveness-sentinel`, whose exit 2 is an `asyncRewake` wake and not a deny. The opt-in headless shim runs the same router with `--shim`, through `mcp/trajectory-server/dist/resolve-hook.mjs`. For every registration the router:

1. hands the call to the install `activeInstall` picks — project/local beats user, newest of two project installs, no entry → the invoking plugin root — when that install's `dist/hooks-router.txt` serves the event, part and tool;
2. with `--shim`, exits 0 without running a gate for another project's session or a session the plugin's own hooks already cover (the `plugin-hooks-marker` marker);
3. decides once per call (`src/hooks/router/dedupe.ts`): a `mkdir` lock at `<project>/.claude/<plugin>/locks/events/<sha256>/`, keyed by the event, part and payload, holds the call's `result`, `stderr` and `rc`; a concurrent duplicate replays only a denial and otherwise exits 0 silently. A finished result answers duplicates for `TMB_DISPATCH_WINDOW_S` (default 5 s); the holder writes its `deadline`, and a lock whose holder died is reclaimed once that deadline passes, never before. A sweep prunes results older than `TMB_DISPATCH_TTL_MIN` (default 10 min) and dead locks at most once per `TMB_DISPATCH_SWEEP_S` (default 60 s), timed by `<project>/.claude/<plugin>/locks/events.sweep`. A project with no trajectory DB gets no lock — the gates just run.
4. after the decision writes one `hook_call` row (from_node `hook:router`) and audits every deny it returns (`src/hooks/router/records.ts`): one `hook_denied` row (from_node `hook:dispatch`) per decision — a gate's deny, an exit-2 block or a fail-closed deny — on the task's issue (the calling swe's run, else `tool_input.task_id`), else the system issue `-1`, with `content_json` `{hook, rule, tool, agent_type, task_id, cwd}` (`rule` = the first 200 characters of the reason). A replayed duplicate writes none, and a failed write never changes the decision.

**Gates fail closed.** Every deny-capable registration in `hooks/hooks.json` carries `"onFailure": "block"`, so Claude Code (2.1.295 and later) blocks the action when the hook crashes, times out, or exits non-zero without valid JSON instead of continuing; observe-only hooks keep the default. The router fails closed by gate kind on every client: an enforcement gate's crash, overrun or exit without a decision denies, an advisory gate's is dropped and logged. `mcp/trajectory-server/src/test/hook-onfailure.test.ts` derives which gates can deny from their TypeScript source and fails when a registration that runs one lacks the key.

**Trajectory-server gates run as one ordered group.** Claude Code runs every hooks.json entry for a matcher in parallel, so a gate could act on a call a sibling gate denies. The `mcp__.*trajectory-server__.*` matcher therefore has one registration, the router's trajectory-server group, marked `stopAtFirstDeny`: `agent-arg-matches-caller`, `swe-brief-gate` (which reads the `swe_brief_fetched` sentinel the `task_brief` handler writes), then by tool name `swe-verification-gate` (task_update_status), `reviewer-identity-observe` (validation_record), `cheatcode-install-approval` (cheatcode_install) or `worktree-adopt-guard` (task_provision, task_reopen, task_retry), then `wm-read-before-provision` (task_provision), one after another with the same payload. The first deny — a gate's own or a fail-closed one — ends the group, so a denied call leaves no observation row and no verification run; the `additionalContext` of the gates that allowed is joined into one output. A gate that runs past its deadline is denied with a timeout reason naming infrastructure load rather than policy, so the caller retries instead of treating it as a policy deny (GH 1803).

`src/test/router.test.ts` covers the router: the first deny in group order, fail-closed enforcement gates, the trajectory-server group stopping at its first deny, budgets and dedupe keys. The rule is written up in [`docs/architecture/CONTAINMENT.md`](../../docs/architecture/CONTAINMENT.md).

## TypeScript gates

Every gate is TypeScript (GH 1692); macOS is the bar.

- **Where they live.** `mcp/trajectory-server/src/hooks/`: one `<gate>.ts` per gate, implementing `Gate` from `gate.ts` (payload in, stdout and exit code out). The build bundles `src/hooks/index.ts` to `dist/hooks.js`; `node dist/hooks.js <gate>` reads the payload from stdin, writes the gate's stdout and exits with its code. An unknown gate or an uncaught error prints one stderr line and exits 1, so a fail-closed gate denies, never allows.
- **The registry.** `src/hooks/registry.ts` maps gate names to gates. `build:bundle` writes `dist/hooks-gates.txt` from it (sorted, one name per line) and `dist/hooks-router.txt` from `ROUTER_GROUPS`; never edit either by hand. `liveness-sentinel` is registered directly as `node dist/hooks.js liveness-sentinel`, since its exit 2 is an `asyncRewake` wake and not a deny; `code-reviewer-spawn-note`, `code-reviewer-preflight` and `rework-limit` are run in-process by `agent-spawn-dispatch` (below), `swe-stop-cause` by `swe-atomic-close`, and `tool-output-size` by `swe-atomic-close` and `bro-turn-usage`.
- **The corpus and the golden recordings.** `tests/fixtures/hook-corpus/<gate>/*.json` holds payloads for each gate ported from bash, at least 8. `src/test/hooks-parity.suite.ts` (run in shards by `hooks-parity.shard-<k>of<n>.test.ts`) runs every one through `node dist/hooks.js <gate>` under `LC_ALL=C`, `LC_ALL=en_US.UTF-8` and `LC_ALL=UTF-8`, and fails on a different exit code or stdout (empty, or deep-equal JSON) than the recording of the retired bash gate frozen in `tests/fixtures/hook-golden/<gate>.json`, one entry per payload with one value per group of locales that agree, its paths stored as tokens such as `@SANDBOX@` and `@PLUGIN_ROOT@`. Every parity suite reads its bash side through `goldenBash` (`src/test/golden.ts`), and `hooks-golden.test.ts` fails on a gate or payload with no entry, and on a registered gate with no corpus unless it was born in TypeScript. A gate born in TypeScript (`bash-output-trim`, `code-reviewer-preflight`, `code-reviewer-spawn-note`, `liveness-alert`, `liveness-sentinel`, `no-prose-in-scratch`, `ref-move-reindex`, `rework-limit`, `session-handoff`, `swe-resume-gate`, `swe-stop-cause`, `task-overrun-alert`, `tool-output-size`, `wm-read-before-provision`, `worktree-adopt-guard`) has no recording and is tested on its own.
- **The router, event by event.** A group's gates run one after another, except in a group marked `concurrent` in `ROUTER_GROUPS`, PreToolUse Bash and Write: there every gate starts and all are awaited, each with a deadline at its own start plus the smaller of its budget and the group budget, and outcomes, stderr and context stay in group order, so the first deny in group order answers. That group's `group_budget_ms` is its largest gate budget. The Bash gates' parser gets `parse_allowance_ms` to load; past it the gates start anyway. Only PreToolUse denies with `permissionDecision: deny`; any other event blocks with `{decision: block, reason}`, and the context of the gates that allowed stays in the one output. An unparseable payload blocks only on an event holding an enforcement gate (PreToolUse, SubagentStop); elsewhere it logs to stderr and exits 0. A payload with no `tool_name` (Stop, SubagentStop, UserPromptSubmit, WorktreeCreate) dedupes on the whole payload, SessionStart on its session, and a call no group serves takes no lock. An empty matcher prints as `-` in `dist/hooks-router.txt`.
- **Deny and block text (GH 1914).** Every deny or block reason ends with the agent's next move, exactly one of ` Allowed form: <exact command or call>` (a safe form of the action exists) or ` This is policy: stop and report.` (none does). `src/hooks/lib/deny.ts` is the one builder: `denyJson`/`denyResult` (PreToolUse `permissionDecision: deny`), `blockJson`/`blockResult` (`{decision: block, reason}`) and `structuredDenyResult` take a required `fix: {allowed} | 'policy'`, so a deny that states no next move does not compile; `code-reviewer-preflight`'s reason stays JSON and carries the fix as a `fix` key; the router re-emits a gate's reason through `passthroughDeny`, and its own timeout denies name a retry. `src/test/hook-deny-fix.test.ts` fails on any other non-test file under `src/hooks/` that spells deny or block JSON, and on a reason in `tests/fixtures/hook-golden/` without an ending.
- **Parts.** Claude Code caps each hook's context at 10,000 characters per string, so a gate with big context has its own registration, `node dist/hooks.js <Event> <part>`: a group's `part` in `ROUTER_GROUPS`, a seventh column of `dist/hooks-router.txt` (default groups have none) and the third segment of its `budgets.json` key. SessionStart has `persona` and `prescan`, UserPromptSubmit `persona` and `roundtable`; registrations of one event still run in parallel. Parts of one event dedupe apart, and an install hops a call only to an install whose table has that event and part.
- **Plain text and paths.** On SessionStart and UserPromptSubmit a gate's plain stdout is context: a lone output passes through unchanged, several merge into one `additionalContext` in group order, and only text shaped as JSON that fails to parse is dropped and logged. WorktreeCreate reads stdout as the path, so the router prints the gate's bare path and nothing else; on a gate failure, timeout, budget skip, unparseable payload or failed hop it prints nothing, names the cause on stderr and exits non-zero, and a duplicate replays the path.

## Grouped by lifecycle

### SessionStart — preflight
`ensure-gitignore`, `mcp-health-check`, `deferred-tools-drift-warn`, `plugin-hooks-marker`, `session-start-persona`, `session-start-prescan`, `ensure-mcp-deps-installed`, `substrate-preflight`, `orphan-scan` — make sure the gitignore, MCP server, its `@huggingface/transformers` runtime dependency, and required host binaries are in place before a session does real work, inject bro's persona (the plugin's `CLAUDE.md`, which Claude Code never loads itself, shared with `user-prompt-persona` through `src/hooks/lib/persona.ts`; neither hook writes the project's `CLAUDE.md`), mark the session as running the plugin's own hooks (so the opt-in headless shim yields), warn about pre-1.1.0 TMB hooks left in `~/.claude/settings.json` (the prescan's `Plugin:` line), and say once per session when a user-scope install is ignored for the project's (or recommend `--scope project` when only a user-scope install exists).

Every file a hook writes lives under `<project>/.claude/<plugin>/` (logs, locks, session markers); nothing is written under `$HOME` (`tests/l1-lint/no-home-writes.test.mjs`).

#### `orphan-scan` — project-scoped cross-upgrade orphan scan

Detects (and, only when explicitly opted in, cleans) TMB artifacts left behind by version upgrades. Advisory: it emits findings as `additionalContext`, soft-fails, caps itself with a tight internal timeout, and never blocks session start.

**Project-scoping invariant (load-bearing).** A user may run a *different* TMB version in *other* projects — each with its own cache dir, MCP process, and `trajectory.db`. Those are legitimate, not orphans. The hook resolves the current project first (`projectRoot`: the project holding the resolved trajectory DB, else `CLAUDE_PROJECT_DIR`, never the session cwd → its `.claude/<plugin>/trajectory.db` live path and its `~/.claude/projects/<this-slug>/` history dir) and confines all detection and cleanup to it. It never enumerates, reports, or touches another project's DB, process, or pinned cache version. The single permitted cross-project action is removing a cache version that *no* `installed_plugins.json` entry pins (globally unused).

What it detects, current project only:
1. **Stale old-layout DBs of this project** — `~/.claude/projects/<this-slug>/trajectory.db`, its `memory/trajectory.db`, and a legacy `~/.claude/<plugin>/trajectory.db` only when this project has no live DB yet. A candidate is 0-byte *or* has a `schema_version` older than the live DB. The live `<project>/.claude/<plugin>/trajectory.db` is always kept.
2. **Stale duplicate MCP proc on this project's live DB** — a `trajectory-server` node proc holding *this* project's live DB whose owning Claude Code session is gone. Each holder is traced up its parent chain to the nearest Claude Code process — any word of its command line is `claude` / `claude.exe` by basename (`claude`, `node /x/bin/claude`, the desktop app's `.../MacOS/claude`), a native-installer `.../claude/versions/<v>` binary, or the npm package's `.../claude-code/cli.js`. A holder owned by this session or by another live session is never reported: SQLite WAL lets sessions share the DB. A proc holding any other project's DB is never flagged. `lsof` absence degrades gracefully.
3. **Globally-unused cache versions** — a `~/.claude/plugins/cache/<channel>/<plugin>/<version>` dir referenced by no `installed_plugins.json` entry. A version pinned by any project (current or other) is never a candidate.

**Safety gates.** Detection-first: the default mode reports only and deletes nothing. Cleanup is gated behind `TMB_ORPHAN_SCAN_CLEAN=1` (default OFF) and is limited to this project's provably-dead stale DBs, a confirmed stale duplicate proc on this project's live DB (with a `kill -0` liveness check), and globally-unused cache versions. It never removes the live DB, never touches another project's DB / proc / cache, and never removes a pinned version. The scan is idempotent and soft-fails. (Tests set `TMB_ORPHAN_SCAN_HOME` / `TMB_ORPHAN_SCAN_PROJECT_DIR` to sandbox HOME and project-root resolution.)

#### Cheatcode status reconciliation (trajectory-server)

The trajectory-server sets each `cheatcodes` row's `status` to `active` or `broken` from runtime evidence and writes a `cheatcode_healthcheck` audit row per change, at every server start (in the background, so startup is not delayed) and on demand through bro's `cheatcode_reconcile` tool. Names always match exactly, never as a substring (`tmb` never matches `tmb-x`):
- `skill` — `file_path` exists on disk.
- `mcp` with `source_url` `mcp:<plugin>/<server>` (a plugin-bundled server, as `/scan` records it) — `claude plugin list --json` has an entry whose `id` before `@` is `<plugin>`, it is `enabled`, and its `mcpServers` has the key `<server>`.
- any other `mcp` row — the name is a server name in `claude mcp list` or a `~/.claude.json` `mcpServers` key.
- `plugin` — `claude plugin list --json` has an enabled entry whose `id` before `@` is the name.

Only `active` and `broken` rows are reconciled. A row whose evidence source is unavailable (no `claude` CLI, a timeout, an unparseable plugin list, no MCP listing) is left untouched. Each `claude` listing is fetched once per reconcile and bounded by `TMB_CHEATCODE_HEALTHCHECK_TIMEOUT` seconds (default 4). Startup always reconciles skill rows. It runs the `claude` listings only when an `active` or `broken` mcp or plugin row exists, and then only if the CLI config fingerprint changed or `.claude/tmb/cheatcode-probe.json` is missing, corrupt or older than 24 h. The fingerprint is a sha256 over the `mcpServers` maps, `.mcp.json`, `enabledPlugins` and `installed_plugins.json`. `cheatcode_reconcile` always probes and refreshes that cache. Bypass for the startup run: `TMB_DISABLE_CHEATCODE_HEALTHCHECK=1`.

### UserPromptSubmit — per-turn setup + routing
`user-prompt-persona`, `activation-routine`, `session-log-capture`, `prompt-intent-hints`, `roundtable-slash-detect` — inject bro's persona once in a session that started without it (plugin hooks reloaded mid-session; a one-time notice to start a new session when the plugin's `CLAUDE.md` cannot be read), inject identity/context (plus the HALT + recovery pointer when the trajectory-server is not running at the prompt, and `session_id=<id>` for bro's planning calls), log the turn, and route phrasing hints (onboarding nudges, roundtable detection). Harness turns — task/system notifications, subagent hand-backs, agent and cross-session messages — never fire a hint, record `/roundtable`, or activate bro mode by mentioning bro; hints match only the prompt's unquoted text.

`prompt-intent-hints` intents, in priority order (the first match wins; each has a `TMB_DISABLE_*_HINT=1` bypass): `cheatcode-install`, `consultant-spawn`, `search-grounding`, `concerns-protocol`, `push-intent`, `reonboard-intent`, `headless-intent` (`TMB_DISABLE_HEADLESS_HINT`; `claude -p`, headless or CI-run phrases on an onboarded project whose `headless_enforcement` is not `yes` — bro asks one consent naming `.claude/settings.local.json` and the entry count, then calls `onboard_apply(headless_enforcement='yes')`), `resume-intent`, `adr-required` (`port … to` and `rewrite … in` match `port`/`rewrite` as whole words), and `audit-intent` (`TMB_DISABLE_AUDIT_HINT`) — the whole words audit, verify, check, double-check or architecture point bro to `tmb_audit` and outputs-first work.

### PreToolUse — gates (deny on violation)
Git: `git-guards`, `git-push-guard`, `no-remote-auth-guard`, `stay-on-base-guard`, `no-source-edit-from-main`, `no-worktree-branch-create`, `branch-up-to-date-with-remote`, `commit-msg-lint`. Every Bash gate judges the command's executable statements only (`cmdStatements` in `src/hooks/cmd-analysis/`): text inside heredoc bodies and quotes is data, while a `$( )` or backtick inside double quotes runs, so its body is split into statements of its own (its heredoc bodies still data). Each statement runs in its effective dir — its `git -C <path>`, else a preceding `cd <path>`, else the payload cwd when that cwd belongs to a single checkout or lies inside a linked worktree (its git dir differs from the common dir, GH 2510); when the repo has linked worktrees and the statement names no dir from its main checkout, or names its dir through a variable the gate cannot resolve from any cwd, a gate that needs its branch denies with `ambiguous_git_target` and the remedy (`git -C <path>` or `cd <path> && …`). `git-push-guard` reads a git statement as no push only when its subcommand and every git option before it are literal text; an expansion, a brace or glob pattern, or a redirect there (`git $p`, `git "$@"`, `git $(…)`) is denied with `ambiguous_git_subcommand` (GH 2634), as is an option there that is none of git's known global options (GH 2647); git counts by its basename (`/usr/bin/git push` is a push). An expansion in the argument of a value-taking option (`-C`, `-c`, `--git-dir`, `--work-tree`, `--namespace`, `--attr-source`, …) leaves the subcommand known only inside double quotes, or where the variable comes from a literal assignment in the command with no blank, glob, brace or quote character: `git -C "$W" status` and `W=/x; git -C $W status` pass, while `git -C $W status` with `$W` unresolved or holding a blank is denied, since bash may split `$W` into words that move the subcommand (GH 2643). The listing also finds a push behind a leading redirect (`>out git push`, `2>&1 git push`, `<&0 git push`), a `builtin` prefix or an `env -C` dir, and in each `$( )` or backtick of an unquoted heredoc body (`<<` and `<<-`; a quoted delimiter keeps the body data). Code a statement runs later is listed in `-`, so a push in it is denied with `ambiguous_git_target`: a `trap` action, an `alias` value, a `mapfile` / `readarray -C` or `compgen` / `complete -C` callback, a `compgen -W` word list, and a `PS4` holding `$` or a backtick, which `set -x` expands. When the command names `push`, a statement whose code the guard cannot read is denied with `ambiguous_git_subcommand`: a `bash|sh|zsh|dash|ksh -c` string or `eval` argument built from an expansion (`bash -c "$(…)"`, `eval "$X push"`), a shell that reads its code from stdin (`… | sh`, `bash <<<…`, `bash -s`), a `${…@P}` prompt expansion, a command word that is an expansion (`$G push`), a `PS4` set from an expansion (`PS4=$X`, `env PS4=… bash -x`) or written anywhere but as a literal `PS4=` assignment (`${PS4:=…}`, `printf -v PS4`, `read PS4`, `declare -n p=PS4`, `export PS4`), a variable name a builtin takes from an expansion (`declare "$X=…"`, `printf -v "$X"`, `read "$X"`, `mapfile "$X"`), or code nested past three levels (GH 2635). The agent's role comes from its identity (`agentRole` in `src/hooks/lib/role.ts`), never from a path. The git guards are **registration-scoped**: they resolve each statement's git-root to a `repos` row (via `repoNameForRoot` in `src/hooks/lib/repo.ts`) and only enforce on a registered repo — unregistered sibling trees no-op. The protected set is the Rule 2 union of `protected_branches`, `target_branch`, `pr_target`, and the parent branches of this repo's tasks. The first three are read per-repo from the `repos` row — the `repos` row is the source of truth, with no `plugin_config` fallback — and the last comes from the tasks table. On a detached-HEAD worktree the branch is the newest task whose `branch_id` ends in `/<worktree dir name>` (`taskBySlug`). `git-push-guard` gates a branch's first push (no upstream) on the commits past its target branch: the repo's `repos.target_branch`, else the sole registered repo's, else the remote's default branch (`origin/HEAD`), else `main`. See [`docs/architecture/REPO_RESOLUTION.md`](../../docs/architecture/REPO_RESOLUTION.md).
Agent dispatch: `agent-spawn-dispatch`, `swe-brief-gate` (`task_brief` records the sentinel it checks; on the swe's `task_brief` it binds the spawn's open `agent_runs` row to the subagent's `agent_id`; when every row keyed by that `agent_id` is closed, a swe resumed through `SendMessage`, it writes a `swe_resume_observed` audit row instead, and `task_brief` opens a new row for it with `resumed_from` = its previous row, GH 1742), `swe-verification-gate`, `swe-boundary`, `swe-scope-fence`. Before anything else, `swe-verification-gate` runs the changelog and stale-doc checks (`src/hooks/lib/doc-checks.ts`, GH 2866) on the worktree HEAD against its merge base with the task's PR target (resolved as `code-reviewer-preflight` resolves it, below) and denies on the first that fails with the JSON reason `{check, expected, actual}`. Where they look comes from the project's `.config/tmb/doc-checks.json` as committed at HEAD (`{"version":1,"changelog_dir":"<dir>","doc_paths":["<glob>",...],"tool_sources":["<glob>",...],"tool_name_pattern":"<regex with one capture group>"}`, globs matched with `path.matchesGlob`): `stale_doc_ref` (a path the diff from the merge base deletes or renames, or a tool name it drops from a `tool_sources` file, the first capture group of each `tool_name_pattern` match, still appears in a `doc_paths` file at HEAD; a path the commit's own `.gitignore` files ignore, read from the commit's tree, is untracked build output and not counted, and a path whose ignore check errors counts as removed) and `missing_changelog` (the base or HEAD has `changelog_dir` and the diff adds no file under it). With no file both checks are skipped, with no `changelog_dir` or `doc_paths` that check is skipped, and without both tool keys the tool-name half is skipped; each skip is named in the allow's `additionalContext` with the file and key to add. An invalid file (bad JSON, `version` not 1, an unknown key, a bad value) denies as `doc_checks_config`, naming the file and the shape. This repo's own file holds the plugin's layout. An unprovable state (an unresolvable HEAD, no PR target ref, no merge base) denies as `stale_doc_ref`. When both pass, the leak scan (`src/hooks/lib/leak-scan.ts`, GH 2929) checks only the lines that diff adds, skipping deletions and binary files: secrets by secretlint's recommended preset (bundled into `dist/hooks.js`, inline `secretlint-disable` comments not honored), email addresses (`email`) and `/Users/<name>/`, `/home/<name>/` or `C:\Users\<name>\` paths (`home_path`); it denies as `leak_scan` with every hit as `<file>:<line> <rule>`, never the matched text. `noreply@` addresses, `example.com|org|net` addresses and home paths named `<...>`, `user`, `me`, `you` or `runner` always pass; the project's optional `.config/tmb/leak-scan.json` at HEAD (`{"version":1,"allow":[{"rule":"<rule, optional>","pattern":"<regex>","reason":"<why>"}],"disable_rules":[{"rule":"<rule>","reason":"<why>"}]}`) adds allow entries tested against the matched text and turns rules off, each with a non-empty reason, and an invalid file denies as `leak_scan_config`. A git or scanner failure denies. A doc-check or leak-scan deny records no verification run, and neither `waive_verification_gate_reason` nor any bypass skips these checks. It then runs a task's `verification[]` once per close and records the run in the trajectory DB through `src/hooks/lib/verification-runs.ts`: a `verification_runs` row (source `gate`, `commit_sha` = the worktree HEAD, `budget_s`) when the run starts, a `verification_run_commands` row after each command (exit code, elapsed seconds, the last 20 output lines), then `finished_at`, `exit_code` and `timed_out` — so a killed run still leaves its partial record. When a passing run (exit 0, not timed out) for the same task and worktree HEAD finished within the last hour, and `tool_input.commit_sha` (when given) names that HEAD, the gate allows without running anything and says `verification reused run #N (<finished_at>)`. Otherwise, on a rework commit, `mcp/trajectory-server/dist/hooks/lib/verification-carry.js` (bounded by 10 s of the command budget) names the commands it may carry forward from the task's newest passing run R on an earlier commit P (GH 1950): P is an ancestor of HEAD with no merge in P..HEAD, the worktree is clean, `.config/tmb/verification-inputs.json` (version 1, read at HEAD) is unchanged in P..HEAD, the command is no probe and passed in R, and exactly one map entry's `match` equals it with none of its `inputs` globs (`path.matchesGlob`) matching a changed path. Each carried command is recorded with exit 0, elapsed 0 and output `carried from run #R at <sha12>` instead of being run, and the allow's `additionalContext` names them and R; any failure of the helper runs every command. Concurrent closes of one (task, HEAD) serialize on the run lock `<state>/locks/verify-<task>-<sha>/`; the waiter reuses the holder's run when it passed and runs the commands itself otherwise. When the worktree HEAD does not resolve the gate records and reuses nothing (no row is written): verification[] still runs and the decision says `(not recorded: worktree HEAD unresolvable)`. The budget is `plugin_config.verification_timeout_s` (integer seconds, default 900; `TMB_VERIFICATION_TIMEOUT_S` overrides it), clamped to 1–1800 s; 0 or a non-integer falls back to 900 with a stderr warning naming the value. The budget and the cumulative time count command time only: each record write gets its own 3 s (`VERIFICATION_RECORD_BUDGET_MS`), the start and command writes together at most 9 s (`VERIFICATION_RECORD_POOL_MS`; further command rows are then skipped), and the finish write 3 attempts with a 0.5 s, then 1 s backoff. The gate's timeout in the `trajectory-gates` chain (1830 s) covers the cap + 20 s of record writes + 1 s dispatcher + 5 s for reads and the decision, which `mcp/trajectory-server/src/test/hook-timeout-budget.test.ts` derives from the gate's constants. When every finish attempt fails the decision stands, stderr says the run record is unfinished, and the next run start of any task finishes it as exit 137 once it is past its `budget_s` + 60 s (GH 1814); until then `trajectory_doctor` reports it under `no_unfinished_verification_runs` once it is 2 h old. A failing command — including one that itself exits 124 — makes the gate deny with the command and its position, its exit code, its elapsed and the cumulative time, its lines matching `FAIL|failed|Error|❌` (max 15), then the last 20 lines of its output; only the gate's own timeout wrapper firing (or the budget being spent before a command starts) marks the run `timed_out`, and that deny names the command that was running and the cumulative time. After `verification[]` passes, the gate runs the `probe_cmd` of every `review_findings` row of the task with `severity = 'blocking'` except `wontfix` ones (GH 1737, GH 1955; on a DB below schema v57, which has no `severity` column, every row except `wontfix` ones), in id order, in the worktree under the same budget; a task with no `verification[]` but findings still runs them. A probe that exits 0 on an `open` finding sets it `fixed` with `resolved_at`. Every probe runs, and any failing one denies naming the finding; a failing `fixed` finding is named a regression. Each probe is recorded as a `verification_run_commands` row whose command is `[probe <id>] <probe_cmd>`, so run reuse (and `review_handoff`) counts a run only when it also covered the task's current findings. Once verification passes, the gate runs the close lints (`src/hooks/lib/close-lints.ts`, GH 2570): each lint in `.config/tmb/close-lints.json` at HEAD, from the worktree, within the time verification left, recorded as one `lint_runs` row (source `gate`, against the merge base with the PR target, with the fingerprint of the files its `fingerprint_inputs` match) and a `lint_run_results` row per lint. A failing lint denies naming each one with its exit code and last 15 output lines, a lint the budget kills records 124, a malformed config denies, and a passing run of the same commit, base and fingerprint is reused. With no config the run holds no results. `code-reviewer-preflight` admits a reviewer only on this record.

`swe-boundary` judges an swe's Bash writes by the same rules as its Edit/Write calls. Every path a statement writes (`writePaths` in `src/hooks/cmd-analysis/`: `>`, `>>`, `>|`, `&>`, `exec N>`, a heredoc's redirect, `tee`/`tee -a`, every file of `sed -i`/`perl -i`, `dd of=`, `truncate`, the cp/mv/install/rsync/`git mv` destination and the source a mv removes, link/mkdir/rm/touch paths, the dir a command runs in by option (`tar`/`make -C` or `--directory`, `env -C`, `npm --prefix`), the working tree of a mutating git (add, am, apply, checkout, cherry-pick, clean, commit, merge, pull, rebase, reset, restore, revert, rm, stash, switch: its `--work-tree`, else its `-C` dir, else the statement's own dir; status, log, diff, show, rev-parse, fetch, ls-files, branch, worktree list and push write none), python -c / node -e / perl -e / ruby -e one-liners — the path argument of each write call in the program (`open(p, 'w'|'a'|'x'|'+')`, perl `open '>'`, `Path(p).write_*`/`mkdir`/`touch`/`unlink`, `fs.writeFile*`/`appendFile*`/`mkdir*`/`rm*`, os/shutil remove, rename, makedirs, copy* destination, move, rmtree), so a path the program only reads (`open(p)`, `os.listdir`, `sys.path.insert`) is not a target; when a write call's path is not a string literal, its receiver is unknown or the program does not parse, every path-like literal not only read counts instead; a variable is never traced to its binding, since python can rebind a global unseen (`cProfile.run`, `trace`, `pdb`, `gc.get_objects`, pickle), so a program whose write calls all name literal paths has only those as targets (`open('notes.txt', 'w')` beside `s.replace('x', '/user/own')` writes `notes.txt`) while one that writes through a variable counts every literal (GH 1550) — plus their argv operands, and the same for a program fed to python / node / perl / ruby through a heredoc or here-string, or to sh / bash with `-s` or no script, whose redirects and write commands count; a data heredoc such as `cat > f <<EOF` is never read) is resolved against that statement's own `cd` / `git -C` dir. `$VAR` / `${VAR}` / `${VAR:-def}` in a path resolve from assignments earlier in the same command (`$PWD` is the statement's own dir, `$OLDPWD`, within the `&&` chain of a `cd`, the dir before it — `cd -` swaps them — and unresolvable elsewhere, since a failed `cd` leaves the shell's own; `$HOME`, `$TMPDIR` and a `VAR=value` prefix's own command keep the host values, as in the shell); a `for` / `while read` loop variable fed by an in-root glob or by `$(find|ls|git ls-files|git diff --name-only|rg --files|fd …)` (`for f in $(…)`, `src | while read f`, `while read f; do …; done < <(src)`) whose every literal path argument (else the dir it runs in) is inside the run root is judged where its files lie, `"$f"`, `"$f.bak"`, `"${f%.txt}.out"` and `"$f/…"` alike (the listed path itself counts, so `"$f/.."` and `"$f.bak"` of the root are outside it; a source under a prompt-surface dir, a `-name` pattern such as `CLAUDE.md`, or a recursive listing that starts above the root's `agents/`, `skills/`, `commands/`, `templates/`, `rules/` or its `CLAUDE.md` without excluding each whole subtree (`-not -path '*/agents/*'`, `-path '*/agents' -prune`, `--glob '!agents/**'`, `fd -E agents`, `:!agents`; a deeper path excludes nothing; `-iname` / `--iglob` patterns match case-insensitively) reaches the prompt-surface rule, denied for a non-`prompt_bearing` swe as "a loop or glob over <dir> reaches prompt-surface paths"); a target behind a variable the command does not set (or one built by `$( )`) is denied for a non-`prompt_bearing` swe with `BLOCKED: write target "<target>" cannot be judged: depends on a variable the guard cannot resolve in this command; …`. A path on the prompt surface (`isPromptSurfacePath` in `src/hooks/cmd-analysis/surface.ts`: CLAUDE.md, or a `.md` whose repo-root-relative path starts with `agents/`, `skills/`, `commands/`, `templates/`, `rules/` or `.claude/{agents,skills,commands,rules}/`, so `src/agents/x.md` is not surface; the root is the path's `.claude/worktrees/<name>` worktree, else its main git root, and a path with no resolvable root keeps the unanchored match) is denied unless the task is `prompt_bearing`, and `CLAUDE.md` at the worktree root is denied always (Edit/Write too). After a swe edit it runs the lints the file's repo declares in `.config/tmb/edit-lint.json` on that file, `bash -c '<command> "$TMB_EDIT_LINT_PATH"'` from the repo top with the relative path in that env var, and blocks on the first failure; a malformed config or a lint killed at the gate's budget gives a note.

`bash-output-trim` (TypeScript only, GH 2193; `src/hooks/bash-output-trim.ts`) is an advisory gate that runs first in the router's PostToolUse Bash group. It cuts the long output of bro's routine reads before that output enters context. It acts only in bro's main thread (no `agent_id` in the payload), and only on a command it can prove is a read. A quote-aware tokenizer reads the command. Quotes, and backslash escapes inside double quotes, hide the characters below, so `grep 'a|b'` and SQL holding `;` or `|` are fine. Outside quotes, the command must hold no unclosed quote, backtick, `$(`, `<(`, `>(`, `<`, `<<`, `(`, `||`, lone `&`, or redirect other than a stage's trailing `2>&1` or `2>/dev/null`. Every `$` must be a plain `$NAME` or `${NAME}`. The command splits on top-level `&&`, `;` and newlines. Each segment must be one of these:
- `cd <word>`;
- `[export] NAME=<word>`;
- a pipeline whose stages may carry `NAME=<word>` prefixes.

The pipeline's first stage is a read source:
- any filter below;
- `ls`, `echo`, `printf`, `diff`;
- `rg` without `--pre` or `--pre-glob`;
- `git [-C <path>] log|status|diff|show|grep|ls-files|rev-parse|merge-base|blame|shortlog|ls-tree` with no `--output`;
- `gh {pr,issue,run} {view,list,checks,diff}` with any flags, `--json`/`--jq`/`-q`/`--template` included;
- `sqlite3 -readonly <db> <sql>`, the SQL last and starting with `SELECT` or `WITH`.

Every later stage is a filter: `head`, `tail`, `grep`, `sort` without `-o`/`--output`, `uniq` with at most one positional, `cut`, `wc`, `nl`, `cat`, `tr`, `column`, `jq`, or `sed -n` with a print-only script. A print-only script is `p` commands, each with an optional `N`, `N,M`, `$` or `/re/` address, joined by `;`. `sed -i` and every `w`, `W`, `e`, `r` or `s` command are rejected. The program word and the git/gh verb words must be literal. A pipeline whose last stage is a bare `cat` (no arguments) is left whole, so the marker's `| cat` escape gives the full output.

stderr must be empty, and `interrupted` and `isImage` not true. When stdout is longer than 4000 characters, the gate keeps whole head lines within 2400 characters and whole tail lines within 800. Between them it puts one marker line, `[bash-output-trim: cut <n> lines (<c> chars) of <total> lines; rerun with a narrower command, or append | cat for the full output]`. It answers with `hookSpecificOutput.updatedToolOutput`: the `tool_response` with only `stdout` replaced. Any other call, or an output its head and tail would cover whole, gets no output. It never denies.

#### Metering — `agent_runs`
Each swe / code-reviewer `agent_runs` row covers `[started_at, completed_at)` of one agent's run on one task, and every token column is a per-message sum over the run (messages grouped by id, so content-block lines count once); the server opens and closes those rows (the Agent spawn hook `record-swe-spawn` opens swe rows, and `task_brief` opens one when the spawn did not, with `root_dir` and `host`; `bro_atomic_close`, a terminal `task_update_status` and `task_recover` close them with an `exit_reason`), the hooks only measure — tokens plus the run's dominant `model` (the transcript model with the most tokens). Bro lives per session, not per task, so its one row per session is written by its Stop hook alone; per-task cost is the task's swe + code-reviewer rows.
- `bro-turn-usage` reads `session_id` + `transcript_path` from the Stop payload and keeps exactly one bro row per session: `agent_type='bro'`, `task_id` and `issue_id` NULL, `session_id` the payload's, `usage_source='transcript'`, `host='claude'`, `exit_reason='completed'`, `started_at` / `completed_at` the first / last main-loop message, `model` the one with the most tokens, `root_dir` the project holding the trajectory DB (else NULL), and the token columns the sums of the transcript's main-loop assistant usage (content-block lines of one message counted once). One `dbWrite` (`src/hooks/lib/audit.ts`) transaction rewrites the row with absolute sums, or inserts it when absent, so a re-run changes nothing and another session's row is never touched; a session with no real model (only `<synthetic>` messages) or no output tokens writes no row, and a row an earlier Stop wrote stays as it is. Per-task bro rows from older versions are left as they are. After the write it calls `tool-output-size` in-process, fail-open: the recorder that rewrites the session row's `agent_run_tool_output` rows from the whole session transcript (below). The `Stop` registration is the one `async: true` entry of `hooks/hooks.json`, so the hook does not block the turn and its runs can overlap: the UPDATE and the recorder's rewrite change nothing when the row's `completed_at` is later than the run's (an equal one still writes), and a lost run is recovered by the next, which re-reads the whole transcript, so a session never resumed can stay one turn short. A resumed spawn's stop updates its newest keyed row: when that is a resumed row (`resumed_from` set by `task_brief`), only the transcript entries timestamped from its `started_at` on are metered. A `running` task whose `tasks.checkpoint` was written in this run (`checkpoint.at` at or after the transcript's first entry) is a checkpoint handback: it stays `running`, commits or not, and bro gets context to resume swe from `task_brief.checkpoint` (GH 1905). Otherwise a `pending` or `running` task whose transcript holds a live background command (`liveBackgroundIds` in `src/hooks/lib/background-wait.ts`: a `Command running in background with ID: <id>` or `moved to the background (ID: <id>)` start, counted only from the tool_result of a Bash tool_use (GH 2688), with no `<task-notification>` for that `<task-id>` carrying a `<status>`, and no `TaskStop` on it) keeps its status, commits or not, with one `swe_atomic_close_background_wait` audit row (`task_id`, `commit_sha`, `background_ids`) and context telling bro that swe's resumed turn closes it; an unreadable transcript skips this check (GH 2206). A SWE stopping while `failed` gets metrics only. ## How it fits

Hooks are TMB's enforcement substrate: they make the workflow doctrine mechanical instead of advisory. A PreToolUse deny is a hard stop for the agent that tripped it. Hook behavior is covered by L3 (`tests/l3-integration/hooks/`).

Audit rows carry their author, and the gates trust only the author the event allows. Each line of `lib/audit-events.txt` is `event<TAB>writers` (generated from the `writers` of `mcp/trajectory-server/src/audit-events.ts`); `auditAppend` / `auditSql` write a `hook:<name>` row only for events listing `hook` (`system` only for events listing `server`), else fail with code 2 and `audit_event_not_writable_by_role`, and name the file when it is missing or unreadable. The check is `auditWriterCheck` in `mcp/trajectory-server/src/hooks/lib/audit.ts`. A hook reading a waiver as authorisation requires the bro-authored row: `close-issue-on-merge` (`GATE_SKIP_RECORDED_SQL` in `src/review-sql.ts`) counts a `review_gate_waived` row only when `from_node = 'bro'` and a `review_gate_bypassed` row only from `bro` or itself.
