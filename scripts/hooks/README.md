# scripts/hooks

The Claude Code lifecycle hook engine — the deterministic enforcement layer that gates, nudges, and reacts to what bro and the subagents do each session. Every script reads a hook JSON payload on stdin and either exits silently, emits `additionalContext`, or returns a `permissionDecision: deny`. The wiring (which script runs on which event) lives in the plugin-root `hooks/hooks.json`; the scripts here are the implementations.

## `dispatch.sh` — the one entry point

Every `hooks/hooks.json` command is `"${CLAUDE_PLUGIN_ROOT}/scripts/hooks/dispatch.sh" <gate>` — the placeholder quoted, so a plugin root containing a space stays one word (timeout = the gate's budget + 1 s), and the opt-in headless shim execs `dispatch.sh <gate> --shim`. The dispatcher:

1. runs the gate of the install this project uses — `lib/resolve-install.sh` picks it from `installed_plugins.json` (project/local beats user, newest of two project installs, no entry → the invoking plugin root) — with `CLAUDE_PLUGIN_ROOT` pointing at that install;
2. with `--shim`, exits 0 without running the gate for another project's session or a session the plugin's own hooks already cover (the `plugin-hooks-marker.sh` marker);
3. runs the gate once per (event, payload, gate): a `mkdir` lock at `<project>/.claude/<plugin>/locks/events/<sha256>/` holds the gate's `result`, `stderr` and `rc`; a concurrent duplicate replays only a denial and otherwise exits 0 silently. A finished result answers duplicates for `TMB_DISPATCH_WINDOW_S` (default 5 s); results are pruned after `TMB_DISPATCH_TTL_MIN` (default 10 min); a lock whose holder died is reclaimed once it is older than the gate's timeout. The lock directory and the shim's project comparison use the project's physical path (`cd -P`), so a symlinked project dir and its real path share one lock. A project with no trajectory DB gets no lock — the gate just runs.
4. audits every deny it returns: one `hook_denied` row (from_node `hook:dispatch`) per decision — a gate's deny JSON, an exit-2 block or a fail-closed deny — on the task's issue (the calling swe's run, else `tool_input.task_id`), else the system issue `-1`, with `content_json` `{hook, rule, tool, agent_type, task_id, cwd}` (`rule` = the first 200 characters of the reason). A replayed duplicate writes none, nor does a fail-open gate's exit other than 0 or 2; inside a chain the member's own dispatch writes it. A detached child makes the write after the decision is printed (300 ms busy wait, 600 ms budget, output discarded), so the hook exits without waiting for it and a failed write never changes the decision.

**Gates fail closed.** Every deny-capable registration in `hooks/hooks.json` carries `"onFailure": "block"`, so Claude Code (2.1.295 and later) blocks the action when the hook crashes, times out, or exits non-zero without valid JSON instead of continuing; observe-only hooks keep the default. The dispatcher honours the same key on every client: for a gate registered that way, a missing script, a non-zero exit other than 2 without a deny, or a dispatcher error becomes a deny (PreToolUse) or `decision: "block"` (other events) with exit 0 and a stderr line naming the cause; a deny the gate printed before dying is kept. `tests/l1-lint/hook-onfailure.sh` derives which gates can deny from their source and fails when one lacks the key.

**Trajectory-server gates run as one ordered chain.** Claude Code runs every hooks.json entry for a matcher in parallel, so a gate could act on a call a sibling gate denies. The `mcp__.*trajectory-server__.*` matcher therefore has one registration, `dispatch.sh trajectory-gates` (timeout 1842 s, `onFailure: block`). The chain (`lib/registrations.sh`) runs `agent-arg-matches-caller`, `swe-brief-gate` (which reads the `swe_brief_fetched` sentinel the `task_brief` handler writes), then by tool name `swe-verification-gate` (task_update_status), `reviewer-identity-observe` (validation_record) or `cheatcode-install-approval` (cheatcode_install), one after another with the same payload, each through `dispatch.sh <gate> --chain trajectory-gates` (its own dedupe key and lock, its own timeout from the chain table for the duplicate wait). The first deny — a gate's own, exit 2, or a fail-closed one — ends the chain, so a denied call leaves no observation row and no verification run; the `additionalContext` of the gates that allowed is joined into one output. Each gate runs in its own process group under a watchdog at its chain-table timeout: past it, the group — the gate and everything it started — is killed and the chain denies; any exit other than 0 or 2 also ends the chain with a deny. The watchdog kills only while its chain subshell is alive and the gate's pid still leads its own group, so it never signals a reused pid. A TERM sent to the dispatcher's pid alone lets the running gate finish before the dispatcher exits: the trap that stops the gate's group runs in the chain subshell, which only a signal to the dispatcher's process group reaches. TERM, INT or HUP to that group stops both; KILL to it leaves the gate to run to its end in its own group. When the same event fires twice (a user and a project install), the second chain's duplicate waiter that gives up on the first ends that chain without a decision, so no later gate runs for it. A chain is fail-closed by construction — also without hooks.json, and any gate fails closed when `lib/registrations.sh` cannot be loaded — which matters for the headless shim: `/onboard` copies no `onFailure` into `settings.local.json`, and it now registers `trajectory-gates`, so headless runs get `swe-brief-gate` enforcement too.

**Without jq.** `dispatch.sh` reads a registration's timeout and `onFailure` from hooks.json with awk (`tmb_registration` in `lib/registrations.sh`), so the fail-closed path holds on a host without jq. There a gate registered `onFailure: block` denies with `jq not found` before it runs; the deny-capable gates that check for jq themselves exit 1 with `jq not found` on stderr (the dispatcher turns that into the deny), and the observe-only `reviewer-identity-observe.sh` exits 0 with a stderr note. The SessionStart prescan prints `Tooling: jq not found — every TMB gate will deny until it is installed`.

`tests/l1-lint/hooks-via-dispatcher.sh` keeps every registration on the dispatcher; `tests/l3-integration/hooks/dispatch.test.sh` covers dedup, install resolution, the shim yield, fail-closed gates, the chain, the no-jq path, the deny audit and the TypeScript route. The rule is written up in [`docs/architecture/CONTAINMENT.md`](../../docs/architecture/CONTAINMENT.md).

## TypeScript gates

Gates are moving from bash to TypeScript one at a time (GH 1692); macOS is the bar.

- **Where they live.** `mcp/trajectory-server/src/hooks/`: one `<gate>.ts` per gate, implementing `Gate` from `gate.ts` (payload in, stdout and exit code out). The build bundles `src/hooks/index.ts` to `dist/hooks.js`; `node dist/hooks.js <gate>` reads the payload from stdin, writes the gate's stdout and exits with its code. An unknown gate or an uncaught error prints one stderr line and exits 1, so a fail-closed gate denies, never allows.
- **The registry.** `src/hooks/registry.ts` maps gate names to gates. `build:bundle` writes `dist/hooks-gates.txt` from it (sorted, one name per line); never edit that file by hand. Today it lists `askuserquestion-length-lint`, `containment-guard`, `ensure-mcp-deps-installed`, `pr-reviewer-preflight`, `pr-reviewer-spawn-note`, `rework-limit` and `task-overrun-alert`.
- **Routing.** `dispatch.sh` runs `node <install>/mcp/trajectory-server/dist/hooks.js <gate>` in place of `bash <gate>.sh` when the gate is an exact line of the install's `dist/hooks-gates.txt`, `dist/hooks.js` exists and `node` is on PATH; otherwise the `.sh` runs. Dedupe, locks, chains, timeouts, fail-closed and the deny audit are the same on both routes. The `.sh` stays beside each ported gate as its parity reference. A gate born in TypeScript has no `.sh`: `dispatch.sh` resolves it by its manifest line and runs it only through node (with `TMB_HOOKS_IMPL=bash`, or no `node`, it is not run and the dispatcher exits 1, so a fail-closed registration denies). `task-overrun-alert` is one, registered in `hooks.json`; `pr-reviewer-spawn-note`, `pr-reviewer-preflight` and `rework-limit` are others, run directly by `agent-spawn-dispatch.sh` (below), not through `dispatch.sh`.
- **The corpus and parity.** `tests/fixtures/hook-corpus/<gate>/*.json` holds payloads for each registered gate, at least 8. `src/test/hooks-parity.test.ts` runs every one through `bash scripts/hooks/<gate>.sh` and `node dist/hooks.js <gate>` under `LC_ALL=C` and `LC_ALL=en_US.UTF-8`, and fails on a different exit code, a different stdout (empty, or deep-equal JSON), or a registered gate with too small a corpus. A gate without a `.sh` twin (`pr-reviewer-preflight`, `pr-reviewer-spawn-note`, `rework-limit`, `task-overrun-alert`) has no bash side, so it is outside the parity set and tested on its own.
- **The kill switch.** `TMB_HOOKS_IMPL=bash` runs every gate's `.sh`.

## Grouped by lifecycle

### SessionStart — preflight
`ensure-gitignore.sh`, `mcp-health-check.sh`, `deferred-tools-drift-warn.sh`, `plugin-hooks-marker.sh`, `session-start-persona.sh`, `session-start-prescan.sh`, `ensure-mcp-deps-installed.sh`, `substrate-preflight.sh`, `orphan-scan.sh` — make sure the gitignore, MCP server, its `@huggingface/transformers` runtime dependency, and required host binaries are in place before a session does real work, inject bro's persona (the plugin's `CLAUDE.md`, which Claude Code never loads itself, shared with `user-prompt-persona.sh` through `lib/persona.sh`; neither hook writes the project's `CLAUDE.md`), mark the session as running the plugin's own hooks (so the opt-in headless shim yields), warn about pre-1.1.0 TMB hooks left in `~/.claude/settings.json` (the prescan's `Plugin:` line), and say once per session when a user-scope install is ignored for the project's (or recommend `--scope project` when only a user-scope install exists).

Every file a hook writes lives under `<project>/.claude/<plugin>/` (logs, locks, session markers); nothing is written under `$HOME` (`tests/l1-lint/no-home-writes.sh`).

#### `orphan-scan.sh` — project-scoped cross-upgrade orphan scan

Detects (and, only when explicitly opted in, cleans) TMB artifacts left behind by version upgrades. Advisory: it emits findings as `additionalContext`, soft-fails, caps itself with a tight internal timeout, and never blocks session start.

**Project-scoping invariant (load-bearing).** A user may run a *different* TMB version in *other* projects — each with its own cache dir, MCP process, and `trajectory.db`. Those are legitimate, not orphans. The hook resolves the current project first (`tmb_project_root`: the project holding the resolved trajectory DB, else `CLAUDE_PROJECT_DIR`, never the session cwd → its `.claude/<plugin>/trajectory.db` live path and its `~/.claude/projects/<this-slug>/` history dir) and confines all detection and cleanup to it. It never enumerates, reports, or touches another project's DB, process, or pinned cache version. The single permitted cross-project action is removing a cache version that *no* `installed_plugins.json` entry pins (globally unused).

What it detects, current project only:
1. **Stale old-layout DBs of this project** — `~/.claude/projects/<this-slug>/trajectory.db`, its `memory/trajectory.db`, and a legacy `~/.claude/<plugin>/trajectory.db` only when this project has no live DB yet. A candidate is 0-byte *or* has a `schema_version` older than the live DB. The live `<project>/.claude/<plugin>/trajectory.db` is always kept.
2. **Stale duplicate MCP proc on this project's live DB** — a `trajectory-server` node proc holding *this* project's live DB whose owning Claude Code session is gone. Each holder is traced up its parent chain to the nearest Claude Code process — any word of its command line is `claude` / `claude.exe` by basename (`claude`, `node /x/bin/claude`, the desktop app's `.../MacOS/claude`), a native-installer `.../claude/versions/<v>` binary, or the npm package's `.../claude-code/cli.js`. A holder owned by this session or by another live session is never reported: SQLite WAL lets sessions share the DB. A proc holding any other project's DB is never flagged. `lsof` absence degrades gracefully.
3. **Globally-unused cache versions** — a `~/.claude/plugins/cache/<channel>/<plugin>/<version>` dir referenced by no `installed_plugins.json` entry. A version pinned by any project (current or other) is never a candidate.

**Safety gates.** Detection-first: the default mode reports only and deletes nothing. Cleanup is gated behind `TMB_ORPHAN_SCAN_CLEAN=1` (default OFF) and is limited to this project's provably-dead stale DBs, a confirmed stale duplicate proc on this project's live DB (with a `kill -0` liveness check), and globally-unused cache versions. It never removes the live DB, never touches another project's DB / proc / cache, and never removes a pinned version. The scan is idempotent and soft-fails. (Tests set `TMB_ORPHAN_SCAN_HOME` / `TMB_ORPHAN_SCAN_PROJECT_DIR` to sandbox HOME and project-root resolution.)

#### Cheatcode status reconciliation (trajectory-server)

The trajectory-server sets each `cheatcodes` row's `status` to `active` or `broken` from runtime evidence and writes a `cheatcode_healthcheck` audit row per change, at every server start (in the background, so startup is not delayed) and on demand through bro's `cheatcode_reconcile` tool. Names always match exactly, never as a substring (`tmb` never matches `tmb-x`):
- `skill` — `file_path` exists on disk.
- `mcp` with `source_url` `mcp:<plugin>/<server>` (a plugin-bundled server, as `/scan` records it) — `claude plugin list --json` has an entry whose `id` before `@` is `<plugin>`, it is `enabled`, and its `mcpServers` has the key `<server>`.
- any other `mcp` row — the name is a server name in `claude mcp list` or a `~/.claude.json` `mcpServers` key.
- `plugin` — `claude plugin list --json` has an enabled entry whose `id` before `@` is the name.

Only `active` and `broken` rows are reconciled. A row whose evidence source is unavailable (no `claude` CLI, a timeout, an unparseable plugin list, no MCP listing) is left untouched. Each `claude` listing is fetched once per reconcile and bounded by `TMB_CHEATCODE_HEALTHCHECK_TIMEOUT` seconds (default 4). Startup always reconciles skill rows. It runs the `claude` listings only when an `active` or `broken` mcp or plugin row exists, and then only if the CLI config fingerprint changed or `.claude/tmb/cheatcode-probe.json` is missing, corrupt or older than 24 h. The fingerprint is a sha256 over the `mcpServers` maps, `.mcp.json`, `enabledPlugins` and `installed_plugins.json`. `cheatcode_reconcile` always probes and refreshes that cache. Bypass for the startup run: `TMB_DISABLE_CHEATCODE_HEALTHCHECK=1`.

### UserPromptSubmit — per-turn setup + routing
`user-prompt-persona.sh`, `activation-routine.sh`, `session-log-capture.sh`, `prompt-intent-hints.sh`, `roundtable-slash-detect.sh` — inject bro's persona once in a session that started without it (plugin hooks reloaded mid-session; a one-time notice to start a new session when the plugin's `CLAUDE.md` cannot be read), inject identity/context (plus the HALT + recovery pointer when the trajectory-server is not running at the prompt, and `session_id=<id>` for bro's planning calls), log the turn, and route phrasing hints (onboarding nudges, roundtable detection). Harness turns — task/system notifications, subagent hand-backs, agent and cross-session messages — never fire a hint, record `/roundtable`, or activate bro mode by mentioning bro; hints match only the prompt's unquoted text.

`prompt-intent-hints.sh` intents, in priority order (the first match wins; each has a `TMB_DISABLE_*_HINT=1` bypass): `cheatcode-install`, `consultant-spawn`, `search-grounding`, `concerns-protocol`, `push-intent`, `reonboard-intent`, `headless-intent` (`TMB_DISABLE_HEADLESS_HINT`; `claude -p`, headless or CI-run phrases on an onboarded project whose `headless_enforcement` is not `yes` — bro asks one consent naming `.claude/settings.local.json` and the entry count, then calls `onboard_apply(headless_enforcement='yes')`), `resume-intent`, `adr-required` (`port … to` and `rewrite … in` match `port`/`rewrite` as whole words), and `audit-intent` (`TMB_DISABLE_AUDIT_HINT`) — the whole words audit, verify, check, double-check or architecture point bro to `tmb_audit` and outputs-first work.

### PreToolUse — gates (deny on violation)
Git: `git-guards.sh`, `git-push-guard.sh`, `no-remote-auth-guard.sh`, `stay-on-base-guard.sh`, `no-source-edit-from-main.sh`, `no-worktree-branch-create.sh`, `branch-up-to-date-with-remote.sh`, `commit-msg-lint.sh`. Every Bash gate judges the command's executable statements only (`tmb_cmd_statements`): text inside heredoc bodies and quotes is data, while a `$( )` or backtick inside double quotes runs, so its body is split into statements of its own (its heredoc bodies still data). Each statement runs in its effective dir — its `git -C <path>`, else a preceding `cd <path>`, else the payload cwd when that cwd belongs to a single checkout; when the repo has linked worktrees and the statement names no dir, a gate that needs its branch denies with `ambiguous_git_target` and the remedy (`git -C <path>` or `cd <path> && …`). The agent's role comes from its identity (`tmb_agent_role`), never from a path. The git guards are **registration-scoped**: they resolve each statement's git-root to a `repos` row (via `lib/resolve-repo.sh`) and only enforce on a registered repo — unregistered sibling trees no-op. The protected set is the Rule 2 union of `protected_branches`, `target_branch`, `pr_target`, and the parent branches of this repo's tasks. The first three are read per-repo from the `repos` row — the `repos` row is the source of truth, with no `plugin_config` fallback — and the last comes from the tasks table. On a detached-HEAD worktree the branch is the newest task whose `branch_id` ends in `/<worktree dir name>` (`tmb_task_by_slug`). `git-push-guard.sh` gates a branch's first push (no upstream) on the commits past its target branch: the repo's `repos.target_branch`, else the sole registered repo's, else the remote's default branch (`origin/HEAD`), else `main`. See [`docs/architecture/REPO_RESOLUTION.md`](../../docs/architecture/REPO_RESOLUTION.md).
Agent dispatch: `agent-spawn-dispatch.sh`, `swe-brief-gate.sh` (`task_brief` records the sentinel it checks; on the swe's `task_brief` it binds the spawn's open `agent_runs` row to the subagent's `agent_id`), `swe-verification-gate.sh`, `swe-boundary.sh`, `swe-scope-fence.sh`. `swe-verification-gate.sh` runs a task's `verification[]` once per close and records the run in the trajectory DB through `lib/verification-runs.sh`: a `verification_runs` row (source `gate`, `commit_sha` = the worktree HEAD, `budget_s`) when the run starts, a `verification_run_commands` row after each command (exit code, elapsed seconds, the last 20 output lines), then `finished_at`, `exit_code` and `timed_out` — so a killed run still leaves its partial record. When a passing run (exit 0, not timed out) for the same task and worktree HEAD finished within the last hour, and `tool_input.commit_sha` (when given) names that HEAD, the gate allows without running anything and says `verification reused run #N (<finished_at>)`. Concurrent closes of one (task, HEAD) serialize on the run lock `<state>/locks/verify-<task>-<sha>/`; the waiter reuses the holder's run when it passed and runs the commands itself otherwise. When the worktree HEAD does not resolve the gate records and reuses nothing (no row is written): verification[] still runs and the decision says `(not recorded: worktree HEAD unresolvable)`. The budget is `plugin_config.verification_timeout_s` (integer seconds, default 900; `TMB_VERIFICATION_TIMEOUT_S` overrides it), clamped to 1–1800 s; 0 or a non-integer falls back to 900 with a stderr warning naming the value. The budget and the cumulative time count command time only: each record write gets its own 3 s (`VERIFICATION_RECORD_BUDGET_MS`), the start and command writes together at most 9 s (`VERIFICATION_RECORD_POOL_MS`; further command rows are then skipped), and the finish write 3 attempts with a 0.5 s, then 1 s backoff. The gate's timeout in the `trajectory-gates` chain (1830 s) covers the cap + 20 s of record writes + 1 s dispatcher + 5 s for reads and the decision, which `tests/l1-lint/hook-timeout-budget.sh` derives from the gate's constants. When every finish attempt fails the decision stands, stderr says the run record is unfinished, and `trajectory_doctor` reports it under `no_unfinished_verification_runs` once it is 2 h old. A failing command — including one that itself exits 124 — makes the gate deny with the command and its position, its exit code, its elapsed and the cumulative time, its lines matching `FAIL|failed|Error|❌` (max 15), then the last 20 lines of its output; only the gate's own timeout wrapper firing (or the budget being spent before a command starts) marks the run `timed_out`, and that deny names the command that was running and the cumulative time.

`swe-boundary.sh` judges an swe's Bash writes by the same rules as its Edit/Write calls. Every path a statement writes (`tmb_cmd_write_paths` in `lib/cmd-analysis.sh`: `>`, `>>`, `>|`, `&>`, `exec N>`, a heredoc's redirect, `tee`/`tee -a`, every file of `sed -i`/`perl -i`, `dd of=`, `truncate`, the cp/mv/install/rsync/`git mv` destination and the source a mv removes, link/mkdir/rm/touch paths, the dir a command runs in by option (`tar`/`make -C` or `--directory`, `env -C`, `npm --prefix`), the working tree of a mutating git (add, am, apply, checkout, cherry-pick, clean, commit, merge, pull, rebase, reset, restore, revert, rm, stash, switch: its `--work-tree`, else its `-C` dir, else the statement's own dir; status, log, diff, show, rev-parse, fetch, ls-files, branch, worktree list and push write none), python -c / node -e / perl -e / ruby -e one-liners — the path argument of each write call in the program (`open(p, 'w'|'a'|'x'|'+')`, perl `open '>'`, `Path(p).write_*`/`mkdir`/`touch`/`unlink`, `fs.writeFile*`/`appendFile*`/`mkdir*`/`rm*`, os/shutil remove, rename, makedirs, copy* destination, move, rmtree), so a path the program only reads (`open(p)`, `os.listdir`, `sys.path.insert`) is not a target; when a write call's path is not a string literal, its receiver is unknown or the program does not parse, every path-like literal not only read counts instead; a variable is never traced to its binding, since python can rebind a global unseen (`cProfile.run`, `trace`, `pdb`, `gc.get_objects`, pickle), so a program whose write calls all name literal paths has only those as targets (`open('notes.txt', 'w')` beside `s.replace('x', '/user/own')` writes `notes.txt`) while one that writes through a variable counts every literal (GH 1550) — plus their argv operands, and the same for a program fed to python / node / perl / ruby through a heredoc or here-string, or to sh / bash with `-s` or no script, whose redirects and write commands count; a data heredoc such as `cat > f <<EOF` is never read) is resolved against that statement's own `cd` / `git -C` dir. `$VAR` / `${VAR}` / `${VAR:-def}` in a path resolve from assignments earlier in the same command (`$PWD` is the statement's own dir, `$OLDPWD`, within the `&&` chain of a `cd`, the dir before it — `cd -` swaps them — and unresolvable elsewhere, since a failed `cd` leaves the shell's own; `$HOME`, `$TMPDIR` and a `VAR=value` prefix's own command keep the host values, as in the shell); a `for` / `while read` loop variable fed by an in-root glob or by `$(find|ls|git ls-files|git diff --name-only|rg --files|fd …)` (`for f in $(…)`, `src | while read f`, `while read f; do …; done < <(src)`) whose every literal path argument (else the dir it runs in) is inside the run root is judged where its files lie, `"$f"`, `"$f.bak"`, `"${f%.sh}.out"` and `"$f/…"` alike (the listed path itself counts, so `"$f/.."` and `"$f.bak"` of the root are outside it; a source under a prompt-surface dir, a `-name` pattern such as `CLAUDE.md`, or a recursive listing that starts above the root's `agents/`, `skills/`, `commands/`, `templates/`, `rules/` or its `CLAUDE.md` without excluding each whole subtree (`-not -path '*/agents/*'`, `-path '*/agents' -prune`, `--glob '!agents/**'`, `fd -E agents`, `:!agents`; a deeper path excludes nothing; `-iname` / `--iglob` patterns match case-insensitively) reaches the prompt-surface rule, denied for a non-`prompt_bearing` swe as "a loop or glob over <dir> reaches prompt-surface paths"); a target behind a variable the command does not set (or one built by `$( )`) is denied for a non-`prompt_bearing` swe with `BLOCKED: write target "<target>" cannot be judged: depends on a variable the guard cannot resolve in this command; …`. A path on the prompt surface (`tmb_is_prompt_surface_path`: CLAUDE/CODEX/CURSOR/GEMINI.md, or a `.md` whose repo-root-relative path starts with `agents/`, `skills/`, `commands/`, `templates/`, `rules/` or `.claude/{agents,skills,commands,rules}/`, so `src/agents/x.md` is not surface; the root is the path's `.claude/worktrees/<name>` worktree, else its main git root, and a path with no resolvable root keeps the unanchored match) is denied unless the task is `prompt_bearing`, and `CLAUDE.md` at the worktree root is denied always (Edit/Write too). Edit/Write outside the worktree is denied. A path inside the worktree but outside the task's `files[]` (an entry covers itself and everything beneath it, never its siblings) is allowed: the first write to it per task brings an `additionalContext` note "`<path>` is outside this task's files[] (`<dirs>`); list it and why in your report" (`lib/scope-fence.sh`, shared with `swe-scope-fence.sh`, which notes Edit/Write the same way and never denies; the marker is `<state>/locks/scope-notes/<task>/`). Scope is judged at close: `bro_atomic_close` diffs the task's own commits (from the merge-base with the base `task_provision` cut from, or with `origin/<pr_target>` when that is newer) against `files[]` and records the extras bro accepts. Reads, and a surface path that is only the read input of a write elsewhere, stay allowed. `no-source-edit-from-main.sh` takes its written paths and surface predicate from the same lib, so the write shapes live in one place. Its enforcement-surface deny (main-checkout edits under `scripts/hooks/` and `hooks/hooks.json`, even for `.md` files and swe) is scoped to the plugin's own source repository: it fires only when the target's git root has a `.claude-plugin/plugin.json` whose `name` equals the running plugin's, so any other project's `scripts/hooks/` follows the ordinary source-edit rules.

Hook-block bypass: when a `PreToolUse` Bash gate judges a command's write targets and denies it, `dispatch.sh` keeps one record per path the command writes (`tmb_cmd_write_paths`) under `<state>/locks/boundary-denies/<session_id>/<sha256 of the canonical path>` (the gate's name and epoch seconds). Only judged denies are recorded: the `BLOCKED: write target "<target>" cannot be judged: …` deny of a `$(parse)`, `$(computed)` or `$(unproven)` target, or of a target behind a variable, substitution or cd the guard cannot resolve (containment-guard and swe-boundary), judged no path and records none, so the Edit/Write on the literal path it prescribes is not flagged (GH 1750, GH 1772; the phrase is `UNJUDGED_PHRASE` in `dispatch.sh` and `containment-guard.ts`, pinned by a test). Records older than `TMB_BYPASS_WINDOW_MIN` minutes (default 10) are pruned on every write. When the same session then Edits/Writes/MultiEdits/NotebookEdits that path inside the window, `swe-boundary.sh` allows the write as before, appends a `hook_block_bypassed` audit row (`content_json`: `tool`, `path`, `denied_gate`, `denied_at`, `session_id`, `task_id`; on the task's issue, else `-1`), removes the record and adds an `additionalContext` telling the swe that a hook block is a hard stop to report to bro. It observes only: no record, no DB or no `session_id` means no output.

Spec contract (`require-task-spec.sh`, run by `agent-spawn-dispatch.sh` on every swe spawn): when the task's `files[]` names a `.sql` file, a `schema.*` file (`schema.prisma`, `schema.graphql`, …), a `db.ts` or a path under a `migrations`, `migration` or `migrate` directory, or its `spec_body` says `add column` or `new` followed by `column` / `tool` / `field` / `table` (case-blind, any whitespace including non-breaking and other Unicode spaces, `-` or `_` between the words), the `spec_body` must carry a `Writer:` line plus a `Populated:` line (the `verification[]` command that proves a non-null sample or a count above zero), or a `Nullable:` line, each with a value; plain, bulleted (`- Writer:`) and numbered (`1. Writer:`) lines all count. The deny names the missing line and the waiver call. The waiver is one `spec_shape_gate_waived` row per task with `from_node = 'bro'` and `content_json` `{"task_id": <N>, "gate": "spec_shape", "reason": "<at least 10 chars>", "waived_by": "bro", "source": "<writer>"}`; `task_id` may be an integer or a numeric string. `task_create_batch` and `task_provision` called with `waive_spec_shape` write it for every task they create (`source` `task_create_batch` / `task_provision`); for an existing task bro records it with `audit_append(event_type='spec_shape_gate_waived', from_node='bro', content_json={"task_id": <N>, "gate": "spec_shape", "reason": "<at least 10 chars>"})` before spawning. swe cannot write it. The gate allows when such a row exists for the task and writes nothing itself; a DB read error denies; `trajectory_doctor` warns on rows the gate cannot read as a waiver — no existing task, or `gate` not `spec_shape` (`spec_shape_waived_rows_name_a_task`).
Spawn effort (`require-spawn-effort.sh`, run by `agent-spawn-dispatch.sh` right after `require-task-spec.sh`): the Agent call's `effort` must be the effort the trajectory DB holds for the spawn. Without jq, or when the DB read fails, it denies; with no trajectory DB or no sqlite3 it allows. A swe prompt with no task id, or one naming no task row, is left to `require-task-spec.sh`.
Containment: `containment-guard.sh` (Write/Edit/MultiEdit/NotebookEdit/Bash) denies a write outside the run's root, chosen by who the caller is, never by its cwd or `$PWD` (GH 1550): for a swe, its task's worktree as `lib/agent-context.sh` derives it — `task_id=<N>` from its spawn transcript (the payload `agent_transcript_path`, else `<transcript_path minus .jsonl>/subagents/agent-<agent_id>.jsonl`, else the `agent_runs` row `swe-brief-gate.sh` bound to its `agent_id`) → `tasks.repo` (empty: the sole `repos` row) → `repos.path` (relative: joined to the project root) → `<repos.path>/.claude/worktrees/<branch slug>`; a swe missing any piece is denied every write (devices aside) with a message naming that piece, audited with `reason` `unbound_caller` and a null root, and never widens to the project; pr-reviewer and bro get the project (`tmb_project_root`: the project holding the resolved DB, else `CLAUDE_PROJECT_DIR`). #### Metering — `agent_runs`
Each swe / pr-reviewer `agent_runs` row covers `[started_at, completed_at)` of one agent's run on one task, and every token column is a per-message sum over the run (messages grouped by id, so content-block lines count once); the server opens and closes those rows (the Agent spawn hook `record-swe-spawn.sh` opens swe rows, and `task_brief` opens one when the spawn did not, with `root_dir` and `host`; `bro_atomic_close`, a terminal `task_update_status` and `task_recover` close them with an `exit_reason`), the hooks only measure — tokens plus the run's dominant `model` (the transcript model with the most tokens). Bro lives per session, not per task, so its one row per session is written by its Stop hook alone; per-task cost is the task's swe + pr-reviewer rows.
- `bro-turn-usage.sh` reads `session_id` + `transcript_path` from the Stop payload and keeps exactly one bro row per session: `agent_type='bro'`, `task_id` and `issue_id` NULL, `session_id` the payload's, `usage_source='transcript'`, `host='claude'`, `exit_reason='completed'`, `started_at` / `completed_at` the first / last main-loop message, `model` the one with the most tokens, `root_dir` the project holding the trajectory DB (else NULL), and the token columns the sums of the transcript's main-loop assistant usage (content-block lines of one message counted once). One `tmb_db_write` transaction rewrites the row with absolute sums, or inserts it when absent, so a re-run changes nothing and another session's row is never touched; a session with no real model (only `<synthetic>` messages) or no output tokens writes no row, and a row an earlier Stop wrote stays as it is. Per-task bro rows from older versions are left as they are. Bypass: `TMB_DISABLE_BRO_TURN_USAGE_HOOK=1`.
- `swe-atomic-close.sh` binds the spawn to `task_id=<N>` from its spawn prompt (`tmb_task_id_from_transcript` in `lib/query-task.sh`, which `swe-brief-gate.sh` shares) for a task in any status; with no id or no such task it writes an `agent_runs_capture_skipped` audit row and stops. It writes the spawn transcript's totals onto the swe row opened for the spawn, keyed `(task_id, spawn_id)` with `spawn_id` = the payload's `agent_id` (`swe-brief-gate.sh` binds the spawn's `tool_use:*` row to it at the first `task_brief`, and reopens it when a resumed spawn briefs again), or inserts a complete row; a re-fire or a resumed spawn's next stop updates the same row. The same transaction marks the task's other zero-token unbound swe rows `unmeasured` and closes them `swept_orphan`: `spawn_id` NULL rows from the spawn's window, and open `tool_use:*` rows older than 90 s (spawns no subagent ever bound); a row bound to an agent id is never matched. The row also takes `host`, the worktree as `root_dir` when unset, and an `exit_reason` from the task's state once the latest stop ended (`completed` for completed/closed tasks, `escalated`, else `failed`). A `pending` or `running` task with commits is auto-completed, with one `swe_atomic_close_auto_completed` audit row (`task_id`, `commit_sha`, `parent_tip_local`, `parent_tip_origin`); a SWE stopping while `failed` gets metrics only. Commits are counted by ancestry: the worktree HEAD has commits only when it is neither equal to nor an ancestor of any parent tip that exists, `refs/heads/<parent>` or `refs/remotes/origin/<parent>` (the repo base when `parent_branch_id` is empty), so a worktree provisioned from `origin/<parent>` beside a stale local `<parent>` is never auto-completed at its base. The swe row copies `tasks.effort` into `agent_runs.effort`. A pr-reviewer stop bound to a task gets one metering row of its own (keyed by `spawn_id`, `root_dir` the project root, `exit_reason` `completed`, `effort` = `plugin_config.reviewer_effort`, high when unset) and no task status change; an unbound pr-reviewer stop writes nothing.

### Not wired in hooks.json
`require-task-spec.sh`, `require-spawn-effort.sh`, `require-feature-branch-active.sh`, `pr-reviewer-after-atomic-close.sh`, `pr-reviewer-no-worktree.sh`, `pr-reviewer-spawn-prompt-shape.sh` — PreToolUse-on-Agent guards (spawn-shape / spec / effort / branch checks) not referenced by `hooks.json`: `agent-spawn-dispatch.sh` runs them, in the order of its header, then the TypeScript gates `pr-reviewer-spawn-note` and `pr-reviewer-preflight` (`node mcp/trajectory-server/dist/hooks.js <gate>`, skipped when `dist/hooks.js` or `node` is missing). `pr-reviewer-spawn-note` (GH 1744) strips the seven `name=value` anchors (`task_id`, `commit_sha`, `branch_id`, `repo`, `repo_path`, `attempt_n`, `subagent_session_id`) from a pr-reviewer prompt, collapses whitespace and denies more than 300 characters of what remains, pointing bro to pass that context as `spawn_note` on `bro_atomic_close` (`task_brief` returns it); other agents pass and `TMB_SKIP_PR_REVIEWER_SPAWN_NOTE=1` bypasses. `pr-reviewer-preflight` judges a pr-reviewer spawn naming `task_id=<N>` (GH 1740) with five deterministic checks on the task's commit, in order, and denies on the first that fails with the JSON reason `{check, expected, actual}`: `sha_mismatch` (`refs/heads/<branch_id>` in the task repo is not `tasks.commit_sha`), `no_passing_run` (no `verification_runs` row for the task and commit with `exit_code=0` and `timed_out=0`), `base_conflict` (`git merge-tree --write-tree <PR target tip> <commit>` exits non-zero; The deny names the ways forward: a decision naming the change of approach, `task_retry` with a redesigned spec, a split, or asking the Human. A DB read failure denies. A deny ends the chain before the PREPARE steps. After the gates pass, it runs two fail-open PREPARE steps: `ensure-swe-worktree.sh` and `record-swe-spawn.sh` (moves a pending task to `running` and opens the spawn's swe `agent_runs` row with `spawn_id` `tool_use:<tool_use_id>`, `session_id` and `effort`; in the same transaction it closes the task's open unbound rows — `spawn_id` NULL or `tool_use:*` — older than 90 s as `swept_orphan`). `require-task-spec.sh` counts such an unbound row as a live swe run for 90 s only: a spawn that started is bound by then (`swe-spawn-bind.sh` at once, else its first `task_brief`). A row bound to an agent id is live however old.

## How it fits

Hooks are TMB's enforcement substrate: they make the workflow doctrine mechanical instead of advisory. A PreToolUse deny is a hard stop for the agent that tripped it. Hook behavior is covered by L3 (`tests/l3-integration/hooks/`).

Audit rows carry their author, and the gates trust only the author the event allows. Each line of `lib/audit-events.txt` is `event<TAB>writers` (generated from the `writers` of `mcp/trajectory-server/src/audit-events.ts`); `tmb_audit_append` / `tmb_audit_sql` write a `hook:<name>` row only for events listing `hook` (`system` only for events listing `server`), else exit 2 with `audit_event_not_writable_by_role`, and name the file when it is missing or unreadable. The check is `tmb_audit_writer_check` in `lib/db-write.sh`; the sqlite3 fallback's `tmb_fallback_audit_append` runs it with the calling agent's role. A hook reading a waiver as authorisation requires the bro-authored row: `close-issue-on-merge.sh` (`_CIM_SKIP_RECORDED`, byte-identical to `GATE_SKIP_RECORDED_SQL` in `tools/lifecycle.ts`) counts a `review_gate_waived` row only when `from_node = 'bro'` and a `review_gate_bypassed` row only from `bro` or itself.
