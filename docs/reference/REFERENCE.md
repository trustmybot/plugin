# Reference pointers

Lookups bro hits occasionally — keep here so they don't bloat CLAUDE.md.

## Where state lives

- **Trajectory DB** — SQLite at `<project>/.claude/<plugin-name>/trajectory.db`. Holds the workflow audit: issues, tasks, discussions, audit, validation, plugin metadata. The `<plugin-name>` segment resolves from `CLAUDE_PLUGIN_ROOT/.claude-plugin/plugin.json`'s `name` field; today that's `tmb` for both stable and RC channels, so both write to `.claude/tmb/`. Project-local, gitignored, per-developer.
- **World model** — the `wm_directories` / `wm_files` tables (plus FTS5 and embedding side tables) in the same trajectory DB. Holds bro's project mental picture: directories with summaries and files with a one-line purpose and content hash, rebuilt by `/scan`. `wm_files.purpose_source` names the purpose's writer: `swe`; a file header (`docstring`, `comment`, `jsdoc`, `frontmatter`, `heading`, `manifest`); the header-less fallbacks `structural` (data files) and `symbols` (code files, from the symbol index); or `none`. The symbol index (`wm_symbols` / `wm_edges`) covers TypeScript, JavaScript, shell, SQL DDL and Perl, whose named subs index as `function` and whose `use constant` names, in both the single and the block form, as `const`; a generated bundle with a sibling source map gets a `bundles` edge to each in-repo source it inlines. See `docs/architecture/WORLD_MODEL.md`.
- **Task specs** — `tasks.spec_body` column, fetched via `task_get(task_id)`. NOT on disk.
- **Typed task fields** — besides the prose spec, a task carries typed scope (`files`) and verification fields that the gates enforce: the scope fence and close-time scope check read the files, the verification gate runs the commands. See `mcp/trajectory-server/src/schema.sql` (`tasks`) for the fields.
- **Issue milestone** — `issues.milestone` column (nullable `TEXT`), a composite FK `(milestone, repo)` into the per-repo `milestones` table (#155, schema v23). See `docs/architecture/ERD.md`.
- **Architectural decisions** — recorded as `kind=decision` discussions in the trajectory DB.
- **Snapshots** — `docs/trustmybot/snapshots/<issue_id>.md`, generated via `issue_snapshot_md`.

## MCP tools (full list)

88 tools across these groups (full schema in `mcp/trajectory-server/src/tools/`):

- **issues**: `issue_create`, `issue_get`, `issue_list`, `issue_close`, `issue_link`, `issue_update_description`, `issue_update`, `issue_resume`, `issue_get_phase`, `issue_sync_retry`, `issue_adopt_remote`, `issue_reconcile_remote`. The write tools return the issue row without its description; `issue_create`, `issue_update_description`, `issue_link` and `issue_adopt_remote` take `include_description: true` to echo it (bro/architect, as on `issue_get`). `issue_adopt_remote` takes an optional `repo` (a `repos` row name) to verify against; a repo-less issue in a multi-repo workspace needs it (`repo_unresolved` otherwise), and a successful adoption backfills the issue's null repo and copies the remote's milestone and labels into columns that are empty locally. `issue_update` (bro) changes an issue's `milestone`, `labels` (a full replacement set, validated like `issue_create`) or `objective` after creation, writes an `issue_updated` audit row with before/after, and mirrors the change to the linked gh/glab issue when `issue_sync` is on; its `_sync` field reports whether the mirror ran. `issue_update_description` mirrors the new description to the linked issue body the same way (the body keeps its sync marker) and reports it in `_sync` too. `issue_reconcile_remote` (bro, optional `dry_run`) closes open local issues whose linked GitHub/GitLab issue is closed on the remote (merged outside a session, closed by hand): it only reads the remote and returns `{checked, closed, deferred, errors, skipped?}`; an issue with live tasks stays open in `deferred` (rerun once they close).
- **milestones**: `milestone_close`
- **tasks**: `task_create_batch`, `task_get`, `task_update_status` (the result carries `return_line`, `status=<status> task=<id> sha=<first 8 of commit_sha, or ->`, the head of swe's final message; an optional `report.wm_feedback` `{answered?, missed?, wrong?}` says what the world model answered, missed or got wrong, and writes one `wm_feedback` audit row, none when every field is blank; only swe may pass it, any other agent is refused with `wm_feedback_invalid`), `task_first_actionable`, `task_rework_analysis` (bro: one typed analysis of a task's FAILs since its last pass, with its root cause, change and whether the findings share one cause in the approach; a newer proven `spec_update`, `effort_raise` or `world_model_fix` clears the two-FAIL rework limit, and `design_drift`, paired with `split` or `retry`, ends the task's swe runs)

- **validation**: `validation_record` (subagent_session_id required when agent='code-reviewer'; the result carries `return_line`, `verdict=<verdict> task=<id> sha=<first 8> attempt=<n> row=<validation row id> findings=<count>`, the head of code-reviewer's final message; an optional `wm_feedback`, the shape `task_update_status` takes, writes one `wm_feedback` audit row, none when every field is blank), `validation_history` (each row carries `findings`, that attempt's `review_findings` with their text, withheld wherever `feedback` is)

symbol hits carry `stale` when the file changed on disk since the last scan), `world_model_symbol` (one symbol's callers, callees, imports, tables read and written, tests and `bundled_by`, the generated bundles that inline its file through a `bundles` edge read from the bundle's source map, plus `symbol.stale`; ## Slash commands

- `/roundtable <topic>` — multi-agent deliberation with checkbox/radio AUQ ratification (full procedure in `commands/roundtable.md`)
- `/onboard` — interactive policy ceremony with two branches based on project shape (local-only vs remote-tracked). Auto-fired on first contact when `plugin_config('onboarded')` is unset; Human-typed for later changes (full procedure in `commands/onboard.md`)
- `/monitor <PR_number>` — invokes `tmb_comment-triage` skill: fetches review comments, plans tasks, dispatches SWE per ratified comment
- `/scan` — triggers `scan_run` to rebuild the world model (`wm_directories` / `wm_files` in the trajectory DB) and refresh the repos registry
- `/tmb:agent-create <role> <question>` — spawns a consultant subagent with the given domain role and seed question

Runtime location: `plugin/commands/<name>.md`.

- `mcp-server.log` — MCP server tool calls
- `mcp-health.log` — SessionStart MCP sample + SubagentStop hook diagnostics
- `issue-sync.log` — `issue_sync_active` warnings + sync errors
- `sql.log` — SQL trace (when enabled)
- `<project>/.claude/tmb/l5-trajectories/<flow>/<run_id>/` — trajectory.jsonl + trajectory.db preserved per flow run (written by `l5PreserveTrajectory` in `tests/l5-l6/lib/flow-helpers.ts`)
- `<project>/.claude/tmb/l6-chain-runs/<run-id>/` — L6 chain runs (`tests/l5-l6/run-l6-chain.ts`; `L6C_RUNS_DIR` overrides)

## Env vars

- `TMB_DISABLE_REMOTE_SYNC=1` — overrides `issue_sync` config to off (defense-in-depth)
- `TRAJECTORY_DB_PATH` — pin DB path for tests/CI (step 1 of [the DB location rule](./TRAJECTORY_DB_LOCATION.md))
- `CLAUDE_PLUGIN_ROOT` — set by CC; resolves plugin name for path calculations
- `TMB_RUN_SILENT_MIN` — minutes of silence before the liveness probe suspects a run or watcher (default 30), times clamp(load1/ncpu, 1, 4)
- `TMB_LIVENESS_POLL_S` — seconds between `liveness-sentinel` polls (default 60)
- `CLAUDE_CODE_SESSION_ATTENDED` — set by CC; `liveness-sentinel` arms only at `1`, since a pending `asyncRewake` blocks `claude -p`

## Hooks (SessionStart / UserPromptSubmit / PreToolUse / PostToolUse / PermissionDenied / Stop / PreCompact / SubagentStart / SubagentStop / WorktreeCreate)

Hook gates in TypeScript, one per `mcp/trajectory-server/src/hooks/<name>.ts` (a row names its source), wired via `hooks/hooks.json`. The nine PreToolUse-Agent gates run through a single `agent-spawn-dispatch` dispatcher rather than as separate registrations. Every gate but one runs through the TypeScript router, one `hooks.json` registration per group (`node dist/hooks.js <Event> [part]`, gates listed in `dist/hooks-router.txt`), one gate after another, except the PreToolUse Bash and Write groups, whose gates run concurrently with the first deny in group order answering. The gate outside the router is the Stop entry `node dist/hooks.js liveness-sentinel`, whose exit 2 is an `asyncRewake` wake and not a deny. The SessionStart default and WorktreeCreate commands open with a `command -v node` guard that, with `node` off PATH, prints `TMB DEGRADED: missing node …` and exits 2 before the router would fail to start (GH 2215). SessionStart's `persona` and `prescan` and UserPromptSubmit's `persona` and `roundtable` are registrations of their own, so each stays under Claude Code's 10,000-character context cap and they still run in parallel. The headless shim runs the same router, one entry per PreToolUse group, as `node dist/hooks.js PreToolUse --shim` ([INSTALL.md](./INSTALL.md)). The trajectory-server group runs `agent-arg-matches-caller`, `swe-brief-gate`, then the tool's own gate, in that order, stopping at the first deny.
