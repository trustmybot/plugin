# plugin_config keys

`plugin_config` is a key → JSON-value table (`key TEXT PRIMARY KEY, value_json TEXT`) for workspace-global settings. bro reads and writes it with `config_get` / `config_set` / `config_list`; `/onboard` writes its answers through `onboard_apply`; hooks read it read-only. A key is any name matching `/^[a-z][a-z0-9_.-]{0,63}$/i`, so the table needs no migration for a new key — but every key the code depends on is listed here.

## Reading the config

The schema-seeded keys are present in every initialised DB via `INSERT OR IGNORE`, which never overwrites a user's choice. The label-taxonomy keys fall back to a generic default in code (`validateIssueLabels`) when unset or malformed, so a label-less project can still create issues. The other keys may be absent until the operation that writes them runs; readers treat absent as the documented default.

## Repo-scoped policy lives on `repos` and `repo_remotes`, not here

Repo-scoped policy lives on the `repos` row (`branching_model`, `target_branch`, `protected_branches`) and in the repo's `repo_remotes` rows — the sole source of truth (#980). There is no global key and no global fallback. `onboard_apply(repo=<name>)` is the only writer of a populated row's `branching_model` / `target_branch` / `protected_branches`; the workspace apply (no `repo`) seeds only rows whose `branching_model` is NULL and never changes a populated row, so rows may differ; `scan_run` keeps `repo_remotes` in sync with each repo's git remotes (#979). `repos.onboard_scan` is not policy: it holds the JSON evidence (branches, origin/HEAD, first-parent merge counts, CI files, CONTRIBUTING.md) and the derived recommendation that `onboard_state_get` rewrites on every call (GH 1575); `onboard_apply` never reads or writes it. See [`REPO_RESOLUTION.md`](../architecture/REPO_RESOLUTION.md).

| Field | Type | Allowed values | Read by | Written by |
|---|---|---|---|---|
| `repos.branching_model` | string | `github-flow` \| `gitflow` \| `custom` | `git-guards.sh`, bro routing | `onboard_apply` |
| `repos.target_branch` (`pr_target`) | string | any valid branch name | `git-guards.sh` PR rule, `git-push-guard.sh`, `branch-up-to-date-with-remote.sh`, `clean-merged-branch.sh`, `cleanup-worktree-on-task-close.sh`, `task_create_batch` (branch base) | `onboard_apply` |
| `repos.protected_branches` | string[] (JSON) | array of branch names | `git-guards.sh` commit rule, `clean-merged-branch.sh` | `onboard_apply` |
| `repo_remotes` rows | one row per `(repo, name)`: `url`, `provider` (`github` \| `gitlab` \| `other`, from the URL host), `is_primary`, `sync` (the onboard Remote choice) | `origin`, else the first remote, is primary; a new row starts at `sync = is_primary` | issue-scoped and milestone sync (`sync = 1` rows only), `substrate-preflight.sh`, `no-remote-auth-guard.sh`, the push gate | `scan_run` (from git remotes, never `sync`); `onboard_apply` (git remotes, and `sync` from its `remote` answer) |

Shell hooks resolve the current repo via `scripts/hooks/lib/resolve-repo.sh` (`tmb_repo_git_root` + `tmb_repo_resolve` / `tmb_repo_remotes`) and read the matching `repos` row. An unset `branching_model` / `target_branch` / `protected_branches` means the repo is not onboarded — run `/onboard` — never a silent global default.

`branching_model` derives the defaults `onboard_apply` writes, and never overrides an explicit value:

| `branching_model` | `target_branch` default | `protected_branches` default |
|---|---|---|
| `github-flow` | `main` | `["main"]` |
| `gitflow` | `dev` | `["main", "dev"]` |
| `custom` | (caller required) | (caller required) |

## Multi-repo workspaces

In a multi-repo workspace the trajectory DB lives at `<workspace>/.claude/<plugin>/trajectory.db` while each git repo lives at `<workspace>/<inner>/`. Repo identity is the `repos` table, and every work table carries a `repo` column that is a real FK to `repos(name)`. Repo selection is per row:

- `task_create_batch` and `issue_create` accept `repo=<name>`; with exactly one `repos` row it is the default. The value must match a `repos.name` row.
- Issue-scoped sync resolves the repo's path and its `sync = 1` `repo_remotes` rows to target an explicit `gh --repo` / `glab -R`, never the server's working directory; a provider with no sync row is never spawned.
- `issue_create` upserts the `milestones(name, repo)` row for an explicit milestone; an omitted milestone defaults to the repo's sole open milestone and never creates a row.
- `onboard_get_questions` / `onboard_apply` take an optional `repo=<name>` to seed from and write to only that `repos` row; omitting it seeds only rows whose `branching_model` is NULL, writes each repo's `repo_remotes` rows (its git remotes, with `sync` set from the `remote` answer), and writes the global `onboarded` / `issue_sync` / enforcement keys. An unknown repo name is a validation error with no partial write.

## Committed team config (optional)

A project may commit `.claude/tmb/config.json` to share defaults across developers:

```json
{
  "branching_model": "github-flow",
  "pr_target": "main",
  "protected_branches": ["main"]
}
```

Onboarding reads the file when present and pre-selects the matching options, so each developer confirms with one click. The file changes only when a developer edits it; each developer's trajectory DB (gitignored) stores their own answer. Identity is per developer and never read from it. See `templates/project-seed/.claude/tmb/config.example.json` for a starter.
