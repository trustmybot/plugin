# dashboard

A local web view of the trajectory DB: issues, tasks, agent runs, gate results (review verdicts and verification runs), the audit feed, a project map of the world model and its concepts. In the issue view the Human can edit an issue, add a comment and close it.

- `server/` — a `node:http` server bound to `127.0.0.1` that opens `trajectory.db` read-only through `node:sqlite` and answers a JSON API under `/api/`. Every read is a `SELECT` in `server/queries.ts`, or in `server/concepts.ts` and the trajectory server's concept functions it calls. Writes (`server/writes.ts`) call the trajectory server's own handlers in-process over a `TrajectoryDB` opened with its default options, which never migrate: an older DB is refused unchanged; the dashboard has no write SQL of its own. The DB path comes from `resolveClaudeDbPath` in `mcp/trajectory-server/src/platform.ts`, the same rule the MCP server uses.
- `web/` — a React + Tailwind + TanStack Query/Table single-page app. It polls `/api/version` (`PRAGMA data_version`) every 2 s and refetches when the DB changes. Colours, fonts and borders come from GitHub's Primer design tokens. The header's colour-mode button cycles auto, light and dark: auto follows `prefers-color-scheme`, and the choice is kept in localStorage under `tmb-color-mode` (absent means auto) and set as `data-color-mode` on `<html>` before the first render. The page is fluid up to 120rem. Tables go through `<DataTable>` (`web/DataTable.tsx`), Primer's DataTable inside a `Box`: an optional filter field with a search icon above it, a muted header row whose sortable headers are buttons carrying `aria-sort`, rows divided by the muted border that highlight on hover, and a `Blankslate` when there are no rows or nothing matches the filter. Clickable rows take focus and open on Enter or Space. Table cells stay on one line: long prose columns (`truncate`) are cut with the full text in `title`, and a wide table scrolls sideways inside its box, never the page. A secondary column sets `hideBelow: 'sm'` or `'md'` to drop out below that breakpoint, so a table fits a 375 px screen. Timestamps render through `RelativeTime` (`<Time>` in `web/Time.tsx` and the `time()` column helper both delegate to it). Issue descriptions, discussion bodies and concept and step descriptions render GitHub-flavoured markdown through `<Markdown>` (`web/Markdown.tsx`, `react-markdown` + `remark-gfm`): raw HTML is skipped, never rendered, and the default URL filter drops `javascript:` links.
  - `web/theme/` — `primer-tokens.css` (generated and committed: the Primer light and dark theme tokens pruned to the families the UI uses), `theme.css` (Tailwind `@theme` names such as `bg-canvas` and `text-fg` mapped to Primer vars, and the `dark:` variant keyed on `data-color-mode`) and `colorMode.ts` (`useColorMode()`).
  - `web/ui/` — components forked from Primer and rebuilt on its tokens, one per file, each opening with a note naming its Primer origin. Styling reads the Primer CSS variables and the `theme.css` names directly; there is no `@primer/react` and no Tailwind palette colour.
    - `AppHeader` (header, live indicator, colour-mode toggle) and `UnderlineNav` (the tabs, with the right edge faded on narrow screens to show they scroll).
    - `Button` (`variant` default, primary, danger or invisible; `size` small or medium; optional `leadingVisual` octicon). It renders a link when given `href`, else a `type="button"` button; `buttonClass(variant, size)` returns its class string.
    - `Label` (GitHub's pill label, nine variants), `StateLabel` (open, closed, not planned or draft, filled, with its octicon) and `CounterLabel` (primary or secondary).
    - `Box`, `BoxHeader` and `BoxRow` (a bordered box with a muted header and divided rows), `Flash` (default, success, warning or danger notice with an icon; danger is announced as an alert) and `Blankslate` (icon, heading, optional description and action).
    - `DescriptionList` (term/detail pairs in a `<dl>`), `Disclosure` (native `<details>`/`<summary>` with a chevron, optionally open) and `CodeBlock` (a focusable, scrolling `<pre>` with an `aria-label`, an optional `maxLines` height and a `CopyButton`; its text is React text only, never markdown or HTML).
    - `NavList` (a vertical nav of links, the current one marked `aria-current="page"` with an accent bar), `ProgressBar` and `StackedProgressBar` (proportional segments in one `role="img"` bar with an `aria-label`).
    - `HelpToggletip` (the `?` help marker, see Page help) and `SegmentedControl` (a `role="radiogroup"` of buttons with a roving tab stop; arrow keys, Home and End move and select).
    - `RelativeTime` (like GitHub's relative-time element): relative text such as "3 hours ago" up to 30 days, each unit floored so 23.5 hours reads "23 hours ago" and 24–48 hours "yesterday", then "on Oct 3" (with the year when it is not this year), with the full timestamp in `title`.
  - `web/shared/` builds on them: `Badge` renders a `Label` whose variant comes from the status, `verdict.ts` maps review verdicts, criterion statuses and finding statuses to `Label` variants (the status is always shown as text too), `Loading` shows errors in a danger `Flash`, and `BUTTON` / `FIELD` are the small default button and the Primer control styles.
  - `web/index.html` applies the stored colour mode in an inline head script before the stylesheet loads, so the page never flashes the wrong theme.
  - `web/views/` — one file per tab (`OverviewView`, `IssuesView`, `IssueView`, `TasksView`, `RunsView`, `AuditView`, `ProjectMapView`); the Project map's Concepts scope is in `web/views/concepts/` (`ConceptSearch`, loaded on demand as its own chunk), the Insights tab in `web/views/insights/` (also its own chunk) and the task page in `web/views/tasks/`. `web/shared/` holds the helpers they share, `help-copy.ts` the help text for each page. `App.tsx` holds only the routing and the help marker slot.
- `dist/` — the committed build: `server.mjs` (one bundled file, no runtime dependencies), `schema.sql` and `schema-eval.sql` (copied from the trajectory server; `TrajectoryDB` reads them beside its module when it opens the write connection, re-applying the current schema idempotently on a DB already at `TARGET_SCHEMA_VERSION`) and `web/` (static assets the server serves).

## Run

```bash
scripts/dashboard.sh
```

Or run `/tmb:dashboard` in a Claude Code session: it starts the same script in the background and reports the URL. Run it from an onboarded project (or set `CLAUDE_PROJECT_DIR`), or point it at a DB with `TRAJECTORY_DB_PATH=/path/to/trajectory.db`. It listens on port 7477; set `TMB_DASHBOARD_PORT` to change it (`0` picks a free port). It prints the URL to open. It binds to loopback only and answers only requests whose `Host` is `127.0.0.1:<port>` (anything else, `localhost` included, is 403), so a DNS-rebinding page cannot read it. Reads need no auth; writes need the per-launch token (see Writes).

## API

| Endpoint | Returns |
|---|---|
| `/api/summary` | open/closed issue counts, tasks by status, running agent count, the 10 most recent runs |
| `/api/issues` | every issue with its task progress |
| `/api/issues/:id` | the issue, its discussions and its tasks (404 when unknown) |
| `/api/tasks` | the most recent 1000 tasks |
| `/api/tasks/:id` | `{ task, issue, validations, findings, verifications, agent_runs }`: the task (spec, `files`, `verification` and `completion_report` parsed from their JSON columns), its issue's `id` and `objective`, its review verdicts and findings, its verification runs newest first (each with `commands` in ordinal order: `ordinal`, `command`, `exit_code`, `elapsed_s`, `output_tail`) and its agent runs with tokens. A JSON column that does not parse is `null`, with the raw text under `<column>_raw`. 404 `task not found` when unknown |
| `/api/agent-runs` | the most recent 200 agent runs |
| `/api/gates` | the most recent 200 review verdicts and 200 verification runs |
| `/api/insights?range=&repo=&agent=&model=&effort=` | `{ range, filters, options, agents, cost, quality, throughput, outliers }` for the Insights tab. `range` is `7d`, `30d` (default), `90d` or `all`; `agent` is `swe`, `code-reviewer` or `bro`; anything else, including the old `reviewer`, is 400. `agents` holds swe and code-reviewer per run and bro per session, each with `n` (runs with measured usage), `total`, a `{ p50, p95, max, avg }` for `tokens_out`, `context`, `cache_hit`, `duration_ms` and `tool_uses` (nearest-rank; p50 and p95 are `null` under 20 runs) and a log-spaced `histogram` of at most 10 buckets. `cost.priced` is `false`, with no amounts, until `model_prices` holds a complete price; `quality` has the first-pass rate, attempts per task, verdict mix, verification pass rate and slowest commands; `throughput` is closed tasks per day; `outliers` the top 10 runs by output tokens, context and duration; each duration row also has `tool_uses`, `tokens_out` and `idle`, with up to 10 idle runs after the top 10 non-idle ones; slowest commands group on the command with whole-string wrapping parentheses and repeated whitespace removed |
| `/api/insights/explore?m=&a=&g=&range=&repo=&agent=&model=&effort=` | `{ measure, agg, dims, groups, review_round_mismatch, days, options }` for the Insights Explore pivot: one measure `m` (`tokens_out` default, `context`, `cache_hit`, `cost`, `duration_ms`, `tool_uses`) under one aggregate `a` (`p50` default, `avg`, `p95`, `max`, `sum`, `count`), grouped by one or two comma-separated dimensions `g` (`agent` default, `model`, `effort`, `repo`, `exit_reason`, `usage_source`, `resumed`, `prompt_bearing`, `task_status`, `day`, `week`, `review_round`, `plugin_version`). The filters are those of `/api/insights`. 400 with `{ error }` on an unknown `m`, `a` or `g`, more than two or repeated dimensions, `cache_hit` with any aggregate but `avg` (it is Σcache_read ÷ Σcontext per group) and `cost` while `model_prices` is empty. Token measures count measured runs only. Each `groups[]` entry is `{ key, n, value }` with `key` one label per dimension, sorted by value descending; p50 and p95 are `null` under 20 runs. One dimension gives at most 10 groups, two give at most 3 panels plus `Other`, each with at most 6 groups plus `Other`. `review_round` numbers each task's code-reviewer runs `1`, `2`, `3+` by start time (`Not a review` for every other run), and `review_round_mismatch` counts the tasks whose code-reviewer run count differs from their highest validation `attempt_n`. `plugin_version` is the run's `agent_runs.plugin_version` when the column exists and is set, else `≈ v<X> (by date)` for the last release dated on or before the run in the `## v<X> — YYYY-MM-DD` headings of the plugin's `CHANGELOG.md` (read once at startup; set `TMB_DASHBOARD_CHANGELOG` to read another file), else `unknown`. `days` is the range's length in days (for `all`, the days since the earliest run); `options` lists the accepted measures, aggregates and dimensions and `priced` |
| `/api/audit?limit=` | the latest audit rows (default 100, 1–1000) |
| `/api/version` | `{ data_version }` for polling |
| `/api/world-model?repo=&path=&depth=` | `{ available, repos, nodes }`: the directory at `path` (default the repo root) and its subdirectories `depth` levels down (default 2, 0–5), each with `repo`, `path`, `parent_path`, `summary`, `file_count`; `repo` defaults to the first repo |
| `/api/world-model/search?q=&limit=` | `{ available, hits }`: FTS5 hits over directory paths and summaries and file paths and purposes, best `bm25` rank first, each with `kind`, `repo`, `path`, `text`, `rank` (default 20, 1–100). `q` is matched as one phrase, so FTS syntax in it is plain text |
| `/api/world-model/graph?repo=` | `{ available, repo, repos, files, edges }`: the repo's `calls`, `imports`, `runs`, `sources` and `instantiates` symbol edges rolled up to file level, same-repo and cross-file only. Each ordered file pair is one edge `{ src, dst, kind, weight }`: `src` and `dst` index into `files`, `weight` counts the symbol edges and `kind` is the heaviest kind among them. `files` holds only files that appear in an edge, each with `path` and `purpose` (one plain line, `''` when none); `repo` defaults to the first repo |

| `/api/concepts?q=&repo=&limit=` | `{ available, repos, repo, concepts, derived }`: saved concepts matching `q` (default 20, 1–50), each with `id`, `name`, `body`, `step_count` and `trust` counts. When none matches, `derived` is an unverified chain read off the call graph, else `null`. A `q` under 2 characters after trimming returns `concepts: []`, `derived: null`; `repo` defaults to the first repo by name |
| `/api/concepts/:id` | the concept with its ordered `steps` (at most 50; `steps_truncated` says when more exist). Each step has `ordinal`, `description`, `trust`, `trust_reason`, `handoff` and `symbol` (`null` when the anchor is gone, then `trust: broken`) |
| `/api/concepts/:id/graph?limit=` | `{ nodes, edges, truncated }`: the step symbols plus their 1-hop `calls`, `sources`, `runs` and `imports` neighbours over exact edges, test and fixture paths dropped (default 60, 1–120). Step nodes are never cut; neighbours fill the rest of the limit in step order. Each node has `id`, `label`, `repo`, `path`, `dir`, `kind`, `line_start` and `step_ordinal` (`null` for a neighbour); each edge `src`, `dst`, `kind` |
| `/api/symbols/:id/neighbourhood?limit=` | the same shape for one symbol and its 1-hop neighbours (default 40, 1–100), used to expand a graph node |

The world-model endpoints pass each `summary`, `text` and `purpose` through `summaryLine` in `server/queries.ts`: the `<untrusted-content>` framing and markdown syntax are removed and the first non-empty line that is not a horizontal rule is returned, at most 160 characters.

The world-model endpoints answer `available: false` with empty arrays (HTTP 200) when the DB has no `wm_*` tables yet (schema below v42).

The concept endpoints answer `available: false` (HTTP 200) on a DB below schema v45 or without the concept tables, and 404 JSON for an unknown id. They call the trajectory server's `searchConcepts`, `getConcept` and `derivedChain` in-process over the read-only connection, so they never write or migrate the DB.

`/api/issues/:id` also returns `label_taxonomy` (`classification` and `priority` lists from `plugin_config`) and `milestones` (names known for the issue's repo) for the edit form.

## Writes

`POST /api/issues/:id/<action>` with a JSON body (`content-type: application/json`):

| Action | Body | Handler |
|---|---|---|
| `edit` | `updated_at` plus any of `objective`, `description`, `labels` (array, one classification and one priority), `milestone` | `issue_update`, then `issue_update_description` for `description` |
| `comment` | `body` | `discussion_append` with `author: human`, `kind: note` |
| `close` | `updated_at` | `issue_close` (no cascade, no waiver) |

Guards, in order:

- `Host` must be `127.0.0.1:<port>` (as for every request) and `Origin` must be `http://127.0.0.1:<port>`; anything else (no `Origin` and `localhost` included) is 403.
- The `x-tmb-token` header must match the token generated at launch and injected into `index.html` as `<meta name="tmb-token">`; otherwise 403.
- Unknown actions or paths are 404, other methods 405, unknown body fields 400. A body over 2 MB is 413 `body_too_large`: the server stops buffering, sends the 413 with `Connection: close` and discards the rest of the upload, so the client receives the response.
- The DB's `plugin_meta.schema_version` must equal the bundled `TARGET_SCHEMA_VERSION`; otherwise 409 `schema_version_mismatch`. The dashboard never migrates the DB.
- `edit` and `close` must send the `updated_at` they rendered; a changed issue is 409 `stale` with the current `updated_at`. The check and the handler's local write run in one `BEGIN IMMEDIATE` on the write connection, so another process cannot change the issue in between; the lock is released before any remote sync. An edit that changes `description` together with other fields runs `issue_update` and `issue_update_description` as two such steps, the second checked against the `updated_at` the first wrote, so a change landing between them is 409 `stale` with `applied: ["issue_update"]`.

A handler refusal is 422 with the handler's `error`, `message` and data (for a refused close, the blocking `tasks`). Each successful handler call adds an `issue_updated` audit row from `dashboard` whose `content_json` carries `actor: human`, `source: dashboard`, `tool` and `fields`. The embedding model is not loaded in the dashboard (`server/main.ts` installs the rejecting loader from `server/no-embeddings.ts` through `setEmbeddingLoader` at startup); the trajectory server's backfill embeds new rows on its next start.

The issue view has an Edit button (objective, description, priority, labels, milestone), a comment box under the discussion, and a Close button for open issues. Errors show the handler's message, any blocking tasks and, for a partly applied edit, the `applied` handlers.

The editor snapshots the issue when it opens. Its fields, the changed-field diff it sends and the `updated_at` it sends all come from that snapshot, never from the live refetch, so a change another session makes mid-edit is never sent back as if the Human had typed it: Save gets 409 `stale` instead. When the live `updated_at` moves past the snapshot, the editor shows a notice that the issue changed; cancel and reopen the editor to load it.

## Page help

Every page, the issue and task pages included, has a `?` marker at the top right of the content. Its accessible name is "About this page: {page}" and it opens a short panel: what the page shows, where its data comes from (the Project map also names its two layers, Structure and Concepts) and a "Use it to" list. It is a toggletip, not a tooltip: it opens after 150 ms of hover, on focus, and on click or tap, and a click pins it open. Escape closes it and returns focus to the button; a click outside closes it, and so does moving focus away unless it is pinned. It stays open while the pointer is over the button or the panel, with 200 ms of grace to cross the gap. Below 640 px the panel spans the screen and scrolls past 60% of its height. The copy lives in `web/shared/help-copy.ts`.

## Project map

The Project map tab reads the world model `/scan` builds. A repo selector drives everything on it, in both search scopes.

A Files | Concepts switch (a `role="radiogroup"` named "Search scope") sits left of the search box and picks what the box searches; switching keeps the query. The URL holds the scope, the query and the selected concept: `#/map?q=…` for files, `#/map?scope=concepts&q=…&concept=<id|derived>` for concepts. Typing updates the URL without adding history entries; switching scope or selecting a concept adds one, so back, forward and a pasted link restore them. Old `#/concepts?q=…` and `#/concepts/:id` links are redirected to the concept scope.

In the Files scope a directory tree loads each directory's children when you expand it (with its README summary and file count), and the search box lists matching folders and files with their paths. On a DB without the world-model tables it says so: open a Claude Code session to upgrade the DB, then run `/scan`.

The Concepts scope searches the concept layer: a concept is a feature traced step by step through the functions that make it up. It replaces the tree and listing with three columns (stacked below 1024 px): results, then the selected concept's steps and graph. Type at least 2 characters; the results list (arrow keys move, Enter selects) shows each concept's step count and trust counts. When no saved concept matches, an unverified chain built from the call graph is offered instead.

Selecting a result shows the concept's trust (the worse of its stored status and its steps' trust, so one broken step makes it Broken) and its steps as a numbered list, each with its function, description, trust badge (Verified, Suspect or Broken) and `path:line`, and a graph beside it: one column per step, each step's neighbours in its column, grouped by directory. `calls` edges are solid, `imports` dashed, `runs` and `sources` dotted, and a plain "then" line joins derived steps with no recorded handoff. Selecting a step highlights its node and clicking a node selects its step; selecting a neighbour offers "Show neighbours" to expand it. "Show as table" lists the edges. Below 1024 px the graph sits behind "Show graph". On a DB without concepts the scope says to run `/scan`. The scope's code loads on demand as its own chunk.

Below both scopes is a file-level dependency graph centred on one focus file, which starts as the file with the most edge weight. Files that use it are on the left ("Used by") and files it uses are on the right ("Uses"), grouped into dashed folder clusters sorted by weight. A folder with more than 5 files shows 4 and a "+N more" node that expands it. Edge width grows with weight and the line style shows the kind: `calls` solid, `imports` dashed, `runs` and `sources` dotted, `instantiates` dash-dot. The header has a file search, a 1 hop / 2 hops switch and the legend. Hovering a file highlights its edges and shows its path and summary; clicking it refocuses with an animation (none under `prefers-reduced-motion`), and the breadcrumbs keep the last 8 focuses. The side panel lists the focus file's dependents and dependencies, sortable by weight or name. Below 1024 px the panel stacks under the graph.

## Task page

Clicking a row in the Tasks tab, or a task id or title in Runs & gates, opens `#/tasks/:id`. The header shows the title, `#id`, status, branch and a link back to the issue. The sidebar lists status, effort, repo, branch, commit and timestamps, then `files[]` and `verification[]`. The main column has the spec (markdown), the success criteria from the completion report (each criterion's status, note or evidence command, plus extras and findings fixed), the reviews (each attempt's verdict and feedback, then the findings with their probe, expected and observed text), the verification runs newest first (the newest open; each command with its exit code, time and output tail) and the agent runs with their tokens. Command output, probes and verification commands are shown as plain text, never as markdown or HTML. An empty section says so in one muted line.

## Insights

The Insights tab (`#/insights/<section>?range=…&repo=…&agent=…&model=…&effort=…&m=…`) charts agent runs in five sections: Tokens, Cost, Time, Quality and Throughput. The URL holds the section, period, filters and the Tokens metric, so a reload or a pasted link restores them; an unknown section opens Tokens. A side nav picks the section (a select below 768 px), with a Period select, a Metric select on Tokens and a "Filters (n)" disclosure for repo, agent, model and effort.

Charts are bars, columns and histograms drawn with visx primitives on Primer tokens. Each sits in a card with a title, a subheader, a legend when it has two or more series and a menu to view the data as a table or download it as `insights-<section>-<range>.csv`. Every chart SVG has `role="img"` and a summary label, and each bar takes focus and shows its tooltip on hover or focus. Tokens shows swe and code-reviewer on one scale and bro on its own, per session; p50 and p95 lines appear from 20 runs, labelled in a band above the plot (end-aligned near the right edge, on two rows when they would touch), below that the card says "Early data". Cost shows amounts only once model prices are set.

Bars are at most 24 px wide with a 2 px gap between neighbours, a translucent wash of the series colour (`--chart-wash` in `web/theme/theme.css`, 0.2 light and 0.28 dark) and a 2 px solid cap on the rounded data end. The agent colours are swe pink, code-reviewer orange and bro blue (`--data-*-color-emphasis`), chosen to stay apart under protan and deutan colour-vision deficiency in both themes; text and values use text colours, never the series colour. Gridlines are solid and horizontal, the baseline is the only axis line and the unit sits in the card subheader. Time shows p50, p95 and max tiles per agent with one slim bar per agent for the average; bro's time and cost are tiles only. Top runs by duration lists the 10 longest working runs first and then up to 10 likely idle runs (at least 30 min with under 1 tool use and under 500 output tokens a minute), labelled "Likely idle". Slowest verification commands groups a command with its subshell form, so `(cd x && y)` counts with `cd x && y`. In the outlier tables the title or command column takes the space left and cuts off with an ellipsis, the full text in its tooltip, so the tables fit a 1280 px window without scrolling sideways.

## Build

Requires Node 22+ and Bun. The server imports trajectory-server source, so run `bun install --frozen-lockfile` at the repo root too for its types. The build type-checks, bundles the server with esbuild, bundles the app with esbuild (code splitting: `app.js` plus lazy chunks under `dist/web/chunks/`) and builds the CSS with Tailwind; every package is a devDependency.

```bash
cd dashboard
bun install --frozen-lockfile
bun run build
```

Commit `dist/` with the source change.

`bun run tokens` regenerates `web/theme/primer-tokens.css` from the pinned `@primer/primitives` with `scripts/primer-tokens.mjs`. The build does not run it; run it after bumping `@primer/primitives` or changing the kept token prefixes, and commit the output.

## Develop

`bun run dev` (in `dashboard/`) rebuilds the server, app and CSS into the gitignored `dist-dev/` on every save and restarts the server when its bundle changes; reload the browser to see a web or CSS change. It listens on port 7488 unless `TMB_DASHBOARD_PORT` is set, so it runs beside an installed dashboard on 7477. Point it at a DB with `TRAJECTORY_DB_PATH=/path/to/trajectory.db`. `dist/` is still produced only by `bun run build`.

## Tests

- `bash dashboard/test/smoke.sh` — seeds a temp DB from `schema.sql`, starts the built server on a free port, checks the page and each endpoint (world-model tree, search and graph included, plus FTS syntax in a search query), and checks the DB file is unchanged; then checks the world-model endpoints answer `available: false` on a DB without the `wm_*` tables.
- `bash dashboard/test/writes.test.sh` — builds a temp DB with `TrajectoryDB` under `$TMPDIR` and a fake `HOME`, starts the built server on a free port and checks each edit, the Human comment, the refused and the allowed close, their audit rows, the stale, token, Origin, Host (on GET too), body-size (the client receives the 413), path and schema-version guards, that the dashboard's `TrajectoryDB` open refuses an older DB and leaves it unmigrated with no backup, and that `server/*.ts` has no write SQL.
- `node --test dashboard/test/concepts.test.mjs` — seeds a temp DB from `schema.sql` with a small symbol index and a 3-step concept whose last anchor is gone, starts the built server and checks concept search (a description word, a derived chain, a too-short query), the detail, the graph and its limit, a symbol neighbourhood, 404s, `available: false` on a v44 DB, and that both DB files are unchanged; then renders the map search field in concept scope (accessible name, concepts placeholder) and the `ConceptSearch` body (a listbox for the picked repo, no field or repo `<select>`, the "No concepts yet" state). `node dashboard/test/concepts.test.mjs --seed <path>` only writes the seeded DB, to view the Concepts scope against it.
- `node --test dashboard/test/map.test.mjs` — renders the Project map to static HTML from a seeded query cache and checks the directory tree, the listing and the empty states; round-trips `mapHash` / `parseMapQuery`, maps `#/concepts` links with `legacyConceptsHash`, and checks the Files | Concepts radiogroup, its arrow keys and the placeholder each scope shows.
- `node --test dashboard/test/tasks.test.mjs` — seeds a temp DB from `schema.sql` with a task carrying a spec, files, verification, a completion report, a failed then a passed review, an open and a fixed finding, a verification run whose output contains `<script>`, and an agent run, plus a task with bad JSON columns.
