### Security
- **A program fed to an interpreter through a heredoc, or a write target held in a variable, no longer slips past the Bash write guards** (GH 1279): `tmb_cmd_write_paths` analyses the heredoc or here-string program of python / node / perl / ruby (with `-` or no script) and of sh / bash / zsh / dash (with `-s` or no script) as it does a one-liner, so `python3 - <<'EOF' … open('/etc/x', 'w') … EOF` is judged on `/etc/x` by `swe-boundary.sh`, `containment-guard.sh` and the files[] note; a data heredoc (`cat > f <<EOF`, `python3 script.py <<EOF`) is still never read. `$VAR`, `${VAR}` and `${VAR:-def}` in a write target resolve from assignments earlier in the same command (`OUT=/x; cat > "$OUT"`, `export`, for loops, one level of nesting), `$PWD` is the statement's own dir and `$HOME` / `$TMPDIR` the host's (a `VAR=value` prefix does not reach its own command's words, as in the shell); a target behind a variable the command does not set, or built by `$( )`, is denied for a non-`prompt_bearing` swe with `BLOCKED: write target "<target>" depends on a variable the guard cannot resolve in this command; inline the path or set the variable in the same command.`, and `containment-guard.sh` (now reading `tmb_cmd_write_paths`, so in-place edits, interpreter writes and each statement's own `cd` dir count) allows it only when the literal directory before the variable is inside the run's root. `tmb_cmd_heredoc_bodies` returns each heredoc body with its delimiter and statement; a here-string (`<<<`) is no longer misread as a heredoc.
