### Fixed
- **A git branch switch, merge, reset or stash pop, or an unzip, that rewrites your project's skills or agents needs the Human's approval** (GH 2987): `unzip a.zip` into the project root or `-d .claude`, and `git checkout`, `switch`, `merge`, `reset --hard`, `cherry-pick`, `revert` or `stash pop` / `apply` that bring in different skill or agent files, could rewrite them with no approval. An unzip is now judged like a `tar` extract; `unzip -l`, `-Z`, `-t` and `-p` write nothing and are not affected. A git move is judged on the files it would actually change: git is asked read-only beforehand, and the move is blocked only when it changes a file under `.claude/skills` or `.claude/agents`, with the deny naming the dir to approve. A move run through `find -exec`, `fd -x`, `xargs`, `watch` (quoted or not), `env`, `sudo`, `timeout`, `nohup` or `sh -c`, or with git named by its path (`/usr/bin/git`), is found the same way the gate finds file writes, and judged the same; one whose ref comes from found files or piped input, or a `stash pop` / `apply` that `watch`, `find`, `xargs` or a loop may repeat, is blocked until the Human approves. Moves whose changes cannot be told before they run (`git pull`, `rebase`, `am`, `apply`, a ref git cannot resolve, a ref the shell fills in, shell text the gate cannot read, or a move beside another git command that may move refs in the same repository) are blocked until the Human approves; the deny suggests running `git fetch` first, then `git merge <ref>` or `git checkout <ref>`, which are judged on their files. Moves in a repository that does not hold the project's skills or agents (such as a nested repo) are not affected and run no extra git command, nor are `git checkout -b`, `switch -c`, `stash list` / `show` / `push`, `merge --abort` and `reset --soft` / `--mixed`. swe is still exempt.
