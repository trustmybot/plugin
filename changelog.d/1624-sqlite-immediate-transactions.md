### Fixed
- **Several sessions can share one trajectory DB without "database is locked" errors** (GH 1624): with bro, PM, SEO, growth and the dashboard each running a trajectory server against the same `trajectory.db`, a write that first read could fail at once with SQLITE_BUSY, and two servers starting together could both run the schema migration. Every write transaction now takes the write lock up front (`BEGIN IMMEDIATE`) so it waits its turn instead of failing, the busy timeout is set before anything else touches the file, and the migration re-checks the schema version under that lock so it runs exactly once. Servers opening a brand-new DB at the same moment now retry the switch to WAL mode instead of failing. The pre-migration `.bak` (and `assert-sql.sh`'s snapshot) is now taken with `VACUUM INTO`, so it includes writes still in the `-wal` file, and a failure to stamp the plugin version at startup is logged and reported instead of being skipped silently.
