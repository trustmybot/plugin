### Security
- **A swe can no longer write outside its own task worktree** (GH 1499): the containment guard, `swe-boundary.sh` and `swe-scope-fence.sh` found a swe's task and root from its cwd or the target path. A spawned swe runs from the main checkout, so its root widened to the whole project and it could write into the main checkout or a sibling task's worktree; a write into a sibling worktree was judged as that sibling's task. The hooks now resolve the caller from the payload `agent_id`, matched to the `agent_runs` row its first `task_brief` binds. A swe with no bound run is denied every write and told to call `task_brief` first, and its `containment_denied` row never names the project root. A bound swe's Bash is judged by the paths it writes, each in its statement's own `cd` dir, not by its cwd, so `cd <worktree> && …` runs from the main checkout while a bare `touch x` there is still denied. pr-reviewer's root is the project, set explicitly. The reported deny of bro's own main-thread writes while its cwd sat in a task worktree came from a stale user-scope hook shim (`~/.claude/settings.json` running the trustmybot-rc 1.0.2 `swe-boundary.sh`, which treated any caller in a worktree as a swe); this release's gates never fence the main thread, and a regression test now covers that case.
