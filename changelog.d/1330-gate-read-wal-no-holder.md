### Fixed
- **Gates read a trajectory DB nobody holds open** (GH 1330): `tmb_gate_read` opened the DB with `sqlite3 -readonly` only, which cannot open a WAL DB whose `-shm` file is absent — the state of a healthy DB while the MCP server is down or restarting — so `require-task-spec`, `swe-verification-gate`, `git-push-guard` and every other gate built on it denied "trajectory DB unavailable" (a fresh session's first swe spawn, headless runs gating before the server starts). Every hook read now goes through `tmb_gate_read` — `tmb_sqlite_ro` (the error-as-empty read behind `swe-verification-gate`'s `verification[]`, `git-guards`, `containment-guard`, `swe-brief-gate`, `remote-id-guard` and others) calls it, and `resolve-repo.sh` reads through `tmb_sqlite_ro` — so no read can come back empty on such a DB and turn a deny into a skip. A WAL DB with no `-shm` is read without `-readonly` (any `-shm`/`-wal` created sit beside the DB, inside the project), as is a `-readonly` read failing with `SQLITE_CANTOPEN` (exit 14); busy, SQL and corruption errors are not retried, `__ERR__` still means unreadable, and `immutable=1` is not used; the SessionStart contract check (`tmb_db_read_budget`) follows the same rule. `tests/l1-lint/gate-read-sql-readonly.sh` holds every SQL those helpers run, including the data-contract SQL, to read-only statements (`SELECT`, `WITH`, or a read of `journal_mode` / `user_version` / `table_info`) and fails any hook that calls `sqlite3 -readonly` itself. The L3 suites of the three gates cover a WAL DB with no holder (with decisions an empty read would flip: a failing `verification[]` that must deny rather than skip, a first push whose range comes from the repos row), with a holder (`-readonly` only), and one no read can open; the GH 1298 fixture runs on WAL again. `trajectory_doctor`'s `spec_shape_waived_rows_name_a_task` also requires `content_json.gate = 'spec_shape'`, matching what `require-task-spec` reads.
