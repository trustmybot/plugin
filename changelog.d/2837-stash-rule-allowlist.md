### Fixed
- **swe and code-reviewer can no longer reach a git stash write through a subcommand the stash rule cannot read** (GH 2837): `swe-boundary` read git's subcommand as written, so `p=stash; git $p pop`, `git $(echo stash) pop` or `git -c alias.s=stash s pop` slipped past the GH 2786 stash rule. The rule is now an allowlist: it admits a git statement only when its subcommand reads literally from the statement's source and, for `git stash`, only a literal `list` or `show`. An expansion, quote or backslash in the subcommand, a path-qualified git, or a `-c` / `--config-env` option that may define an alias is denied with a message asking to spell the subcommand out; a quoted, escaped or computed stash verb is denied as a stash write. An alias set through git's environment config (`GIT_CONFIG_COUNT` / `GIT_CONFIG_KEY_<n>` / `GIT_CONFIG_VALUE_<n>`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_GLOBAL` and the like, as a prefix or an earlier export) is denied the same way, and a command name from an expansion, a substitution or a glob (`$g stash pop`, `$(echo git) stash pop`, `g?t stash pop`) is denied with a message asking to write it literally. A shell alias definition (`alias g='git stash'`, a `BASH_ALIASES` or zsh `aliases` entry, or a variable declared under a name the guard cannot read) and turning on alias expansion (`shopt -s expand_aliases`, `bash -O expand_aliases`) are denied too, since a later literal name could then run git stash; a bare `alias` that only lists and other `shopt` options stay allowed.
