### Fixed
- **A task can record the worktree its swe works in** (GH 2032): when bro runs in a Claude Code worktree session, swe could not write anywhere, because TMB always placed the task at `<repo>/.claude/worktrees/<slug>`. Schema v54 adds `tasks.worktree_path` and `tasks.worktree_adopted`, and every TS worktree reader (task_reopen, task_brief's run row, worktree_commits_fetch, agent-run backfill, repo rename, and the swe-boundary and containment-guard hooks) now uses the recorded path, falling back to the slug path when none is recorded. Adopting a session worktree is not enabled yet: it is built and tested on the server, but no tool reaches it until the TS port of ensure-swe-worktree lands, so every task still runs in its slug worktree as before. The `branch_id_used_on_issue` message from task_provision now says to pick a new name with branch_id_propose, or to call task_provision with `base='<branch_id>'` to stack on it (GH 1731).
