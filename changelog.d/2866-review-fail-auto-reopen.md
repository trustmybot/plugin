### Changed
- **A review FAIL reopens the task on its own** (GH 2866): when code-reviewer records a `fail` verdict, the same transaction moves a completed, needs_validation or closed task of an open issue back to running at effort `high`, with a spawn note naming the blocking findings, so bro spawns the rework at high without asking you. A running task is raised to `high`; a pending, failed or escalated task, or one of a closed issue, is left alone. While a task has a FAIL since its last passing review, a swe spawn below `high` is denied and `task_reopen` refuses a lower effort. A swe spawn of a running task whose worktree is gone is denied until `task_reopen` recreates it, and the rework-limit deny no longer offers an effort raise to a task already at `high`. A disputed FAIL can still be re-reviewed without new code: once no swe run is live, the unchanged commit has a passing verification run and a `re_review` rework analysis is recorded after the FAIL, `review_handoff` restores the task to completed and hands the same commit to a new code-reviewer.
