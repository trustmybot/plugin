### Fixed
- **Every git guard denies a git command whose subcommand it cannot read** (GH 2641): `p=checkout; git $p dev`, `git "$@"` and `git ${p}out dev` were never judged by git-guards, stay-on-base-guard, no-worktree-branch-create, branch-up-to-date-with-remote or swe-boundary, so a commit on a shared base, a branch switch in the main checkout, a `worktree add -b` or an swe's push could slip through behind a variable. Each guard now reads git's subcommand the way the push gate does (GH 2634): where it would judge a literal command of its kind, an expansion, a pattern or a redirect in git's subcommand, or in a git option before it, is denied as an ambiguous subcommand, naming the statement and the literal form to write instead. `git -C "$wt" status` and every other literal command each guard allowed still pass, and a command naming git next to an expansion, or spelling a keyword with quotes inside it (`'git' commit`, `git che''ckout dev`), is no longer skipped by a guard's quick keyword check.
